# TASK_037 - D01 로그 쌍 미확인의 원인 재검증

## 목적

사용자 요청에 따라 로컬 파일명/경로 파싱 오류와 공식 배포 자료의 로그 수집·전처리 범위 차이를 구분한다. D01 부재 처리 정책은 적용하지 않는다.

## 작업 항목

- [x] ZIP 전체 경로·파일명·대소문자·공백·이름 변형·한쪽 파일만 존재하는 경우 점검
- [x] 원본 metric Pod_Name, 활성 CSV/manifest 및 원본 로그 특징 NPY의 이름 대조
- [x] 공개 metric/log 전처리 코드의 입력 범위·필터 확인
- [x] 원시 로그/설정에서 확인 가능한 pod 소유 필드와 타 pod 언급을 구분해 조사
- [x] 확인된 원인·미확정 원인·기존 설명의 수정 사항 기록
- [x] 활성 입력·공식 코드·전처리 설정 보존 검증

## 확인 사항

파일명 유사성은 자동 매핑의 근거로 사용하지 않는다. 로그 파일 부재는 원시 기록 자체의 부재와 구분한다. 다른 pod/노드 로그가 해당 이름을 언급해도 해당 pod가 직접 생성한 로그로 취급하지 않는다. D01/D02 변경·로그 재생성·추론은 미실행이다.

## 결과

로컬 파일명/경로 파싱의 false negative는 발견되지 않았다. 410개 pod는 배포본에 template/structured 모두 없고, 원본 metric 이름은 보존돼 있다. 로그 특징 NPY 10개에도 해당 이름은 없다. 공개 metric/log의 목록 구성은 독립이며 LEMMA 일부 기준선은 교집합을 사용한다. MATMCD도 같은 목록을 사용했는지는 미확정이다.

CC 원자료 configuration에서 누락 72개가 모두 실재하며, node 로그 26개/134,519행을 전수 읽어 3개 pod에 대한 언급을 확인했다. PR 원자료 4개 ZIP 목록을 Range로 조사하고, 2개 날짜의 원시 JSON 8개/75,484개 hit를 확인했다. 표본에 없다는 사실을 원시 자료 전체 부재로 확대하지 않는다.

로그 NPY를 탐색하는 최초 진단은 모든 파일이 중첩 dict라고 가정하여 CC golden signal의 평면 dict에서 AttributeError가 발생했다. 후속 진단은 실제 Node_Name 키와 두 스키마를 명시적으로 구분했다. 또한 CPU 단독 목록을 전체 후보로 간주한 진단을 기존 승인된 다중 metric 합집합 검사로 바로잡고 실패 보고서를 보존했다. 이는 읽기용 진단의 오류이며 기존 D01 파일명 판정에 사용된 경로가 아니다. 원본 NPY·배포 전처리 코드는 수정하지 않았다.

[분석·출처·한계·정정](../docs/D01_LOG_COVERAGE_ANALYSIS.md)에 기록했다. 조사 Task 완료이며 D01 처리 정책 해결/승인이 아니다. 해당 선택은 TASK_035에서 계속 대기한다. 실제 실험·새 로그 생성·후보 삭제는 하지 않았다.
