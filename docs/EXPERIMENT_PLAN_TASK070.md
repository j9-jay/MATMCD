# TASK_070 실행 계획

2026-10-18 작성. 설계 확정 사항은 [TASK_070](../tasks/TASK_070_state_aware_retrieval_experiments.md), 연구 방향은 [연구 로드맵](RESEARCH_ROADMAP.md)을 따른다. 이 문서는 **순서·관문·결정 권장안·비용 추정**을 정리한 계획이다.

**2026-10-18 승인:** 아래 권장안(D-1~D-11)과 E-1~E-3을 사용자가 전부 승인했다. 웹 검색은 무료 할당량을 크게 넘을 것으로 예상되면 생략하고 D-8 대체 경로로 진행한다.

## 1. 전체 흐름

```text
P0 준비 ──→ P1 corpus·출력부 ──→ P2 기준선 파일럿 ──[관문 G1]──→ P3 웹 스냅샷
                                                                      │
P6 평가·보고 ←──[관문 G3]── P5 평가 실행 ←──[관문 G2]── P4 제안 방법 개발 ←┘
```

| 단계 | 내용 | 관련 작업 | 사용 사례 |
|---|---|---|---|
| P0 | 결정(D-1~D-11), RCAEval 다운로드·감사, 카테고리 2 파일 복원 | T1, T2 | — |
| P1 | corpus 구성기, 공통 출력부, 지표, silver label 규칙 | T4, T5, R5 | 개발 사례 |
| P2 | 기준선 파일럿 (PC만, 검색 없는 LLM, flat RAG, MATMCD) | T6, T7 | 개발 사례 일부 |
| G1 | 실측 시간으로 평가 사례 수·설정 고정 | — | — |
| P3 | 웹 스냅샷 수집·누출 검사 (무료 할당량 내) | T3 | 카테고리 2 (+ 선택: 카테고리 1 Diagnosis 문서) |
| P4 | 제안 방법·ablation 개발 | T8 | **개발 사례만** |
| G2 | 제안 방법·프롬프트·상태 설계 동결 | — | — |
| P5 | 모든 방법을 평가 사례에 실행 | T6~T8 | 평가 사례 |
| G3 | 실행 완결성 검사 (실패·누락·조건 일치) | — | — |
| P6 | 지표·통계 검정·오류 분석·보고서 | T9, T10 | — |

관문은 결과를 본 뒤 조건을 바꾸지 않도록 하는 지점이다. G2 이후에는 제안 방법을 수정하지 않는다. 수정이 필요하면 새 버전으로 기록하고 처음부터 다시 평가한다.

## 2. 결정 항목과 권장안

권장안은 제안이며 미적용이다.

| ID | 결정 항목 | 선택지 | 권장안과 이유 |
|---|---|---|---|
| D-1 | 서비스당 여러 메트릭을 한 노드로 묶는 규칙 | (a) 서비스별 메트릭 z-score 평균 (b) 메트릭마다 노드 (c) 서비스당 대표 메트릭 1개 | **(a)** — LEMMA 실행의 로컬 선택과 같고 노드 수가 12~15개로 유지됨. (b)는 OB 69~77개 노드로 쌍이 수천 개 |
| D-2 | RE2-SS의 KPI 열 | 공식 코드 `frontend_latency` | T1에서 실제 열 확인 후 결정. 없으면 공식 코드의 대체 규칙을 따르고 기록 |
| D-3 | 정답 없이 장애 구간 정하기 | (a) 사례 전체 구간(약 24분)을 그대로 사용 (b) KPI 이상 탐지로 시작점 추정 | **(a)** — 사례가 짧아 자를 필요가 적고 새 가정이 없음. 근거에는 시각 메타데이터만 붙임 |
| D-4 | 동적 상태 | A 유형 분류 / B 근거 공백 / C 계획 그래프 / D 데이터 유도 | **A + B 결합.** 카테고리별 상태 유형 목록을 개발 사례로 확정 |
| D-5 | 공유 판단 프롬프트 | 1단계 Yes/No, 근거 인용 요구 | 근거 번호 인용을 요구하는 1단계 판단. 모든 방법 공유. 문안은 P1에서 작성 후 승인 |
| D-6 | RCAEval 개발·평가 분할 | 반복 번호 기준 / 무작위 | **반복 번호 기준:** rep 1(30사례)은 개발, rep 2·3(60사례)은 평가. 서비스 5개 × 장애 6종이 양쪽에 고르게 들어감 |
| D-7 | MATMCD 참고 기준선용 RCAEval 로그 변환 | 로그 템플릿 열 사용 / 템플릿 추출기 사용 / 원문 요약 | T1에서 `log_template` 존재 확인 후 결정. 어느 쪽이든 새 조건으로 기록 |
| D-8 | 웹 할당량 초과 시 대체 | Wikipedia API / 오프라인 corpus | **Wikipedia API** (정식 공개 API) |
| D-9 | 양방향 Yes 처리 | 그대로 제약 전달 / 규칙으로 하나 선택 | **그대로 전달** — 30 Pod 실행과 같은 처리. 발생 수 기록 |
| D-10 | 새 프롬프트의 샘플링 | 기존 값 재사용 / 결정적 설정 | seed 42 유지. 판단 temperature는 P1에서 정하고 모든 방법 공유 |
| D-11 | 반복 실행 | RWR 반복, LLM 반복 | RWR은 그래프 고정 후 반복(비용 작음). LLM 반복은 G1 실측 후 결정 |

## 3. 단계별 상세

### P0 준비

1. **T1 RCAEval 다운로드·감사** — 다운로드 전 파일명·출처·크기 안내 후 허락.
   - 사례 수, 열 이름, KPI, 로그 형식, trace 형식, 정답 필드를 실물로 확인
   - 공개 정보와 다르면 기록하고 결정 항목을 다시 검토
2. **T2 카테고리 2 복원** — 원본 ZIP에서 제외 파일 3개(`GTdatasets_experiment.py`, `Utils/metrics.py`, `data/SampleFromBIF.py`)를 복원하고 `configs/scope.json`을 갱신한다. 5종 데이터와 정답 그래프의 존재를 확인한다. 실행 전 대상 파일을 안내한다.
3. **결정 D-1~D-11** — 사용자 결정 후 설정 파일로 고정.

### P1 corpus·출력부

- **corpus 구성기**
  - 근거 단위: 로그 묶음, trace 호출 관계, 메트릭 이상 요약, 문서 문단
  - 메타데이터: 서비스, 시각, 역할
  - 근거 내용은 모든 방법이 공유하고, 태그와 색인만 방법별로 둔다
- **공통 출력부**
  - 쌍별 판단 → 제약 PC → 그래프 → RWR
  - 기존 검증 코드(PC, RWR, `rca_metrics.py`)를 재사용하고 RCAEval AC@k를 연결
- **silver label 규칙 (R5)** — 정답 근거 = 원인 서비스의, 장애 주입 이후, 원인 지표 유형과 맞는 근거. 정답 정보는 평가 모듈에서만 읽는다.
- **누출 방지 검사** — corpus와 질의에 정답 필드(`root_cause_service`, `fault`, `fault_description`, `inject_time`)가 들어가지 않는지 자동 검사.

### P2 기준선 파일럿 → G1

- 개발 사례 몇 개에서 모든 기준선을 돌려 **호출당 실제 시간과 토큰**을 잰다.
- G1에서 실측값으로 평가 사례 수를 결정한다. 아래 4절의 추정치로 시간이 부족하면, 평가 사례의 무작위 부분집합을 **결과를 보기 전에** 고정한다.

### P3 웹 스냅샷

- **카테고리 2**
  - 변수와 데이터셋 주제로 검색해 스냅샷을 만든다.
  - MATMCD 참고 기준선은 원래 동작대로 자체 반복 검색을 하되 같은 할당량 안에서 기록한다.
- **누출 검사** — 데이터셋 이름, 논문, 저장소, 정답 그래프가 담긴 페이지를 사전 규칙으로 제외한다.
- **사용량 관리** — 사용량을 기록하고 한도 근처에서 멈춘다. 초과하면 D-8 대체 경로로 다시 수집한다.
- **카테고리 1 Diagnosis 문서(선택)** — 공개 트러블슈팅 문서 수집은 필요성과 할당량을 보고 결정한다.

### P4 제안 방법 개발 → G2

- 상태 유형 목록, 상태 생성·전이 규칙, 상태별 검색 질의를 **개발 사례로만** 다듬는다.
- ablation 구성: 상태 제거 / 역할 태그 제거 / 고정 상태 / 동적 상태.
- G2에서 코드·프롬프트·설정 해시를 동결한다.

### P5 평가 실행 → G3

- 모든 방법을 평가 사례에 같은 순서·같은 설정으로 실행한다.
- 실패 시 자동 재시도·입력 자르기·조건 변경을 하지 않고 보고한다(AGENTS.md).
- G3에서 요청 수, 응답 완결, 설정 해시 일치를 전수 검사한다.

### P6 평가·보고

- **지표 4층**: 검색, 답, 귀속, 효율
- **통계**: 사례 단위 paired bootstrap 또는 permutation 검정
- **분석**: 오류 분석, 상태 경로 분석, 30 Pod 근거 누락 사례(동기 예시)
- **보고서**: 원 논문 대비 차이, 미확정 조건, 한계를 함께 적는다

## 4. 비용 추정

가정: 30 Pod 실측 설명 호출 18.67초, 제약 호출 0.87초. 1단계 판단 호출은 근거가 들어가 제약 호출보다 길 것으로 보고 **약 5초로 가정**한다. 모두 P2에서 실측해 대체한다.

| 방법 | RCAEval OB 1사례 (156쌍) | 인과 발견 5종 (596쌍) |
|---|---:|---:|
| PC만 | 수 초 | 수 초 |
| 검색 없는 LLM | 약 13분 | 약 50분 |
| flat RAG | 약 15분 (검색 포함) | 약 1시간 |
| 제안 방법 | 약 30분 (상태 생성 포함, 가정) | 약 2시간 (가정) |
| MATMCD 참고 | 약 1시간 (로그 요약·RAG·설명·제약) | 약 3.5시간 |
| **합계** | **약 2시간** | **약 7.5시간** |

- RCAEval OB 평가 60사례 전체: 약 120시간(약 5일 연속). SS를 추가하면 더 늘어난다.
- G1에서 실측 후 평가 사례 수를 정한다. 예를 들어 서비스×장애 조합마다 1사례를 뽑는 30사례 부분집합이면 약 60시간이다.

## 5. 위험과 대응

| 위험 | 대응 |
|---|---|
| RCAEval 실물이 공개 정보와 다름 (KPI, 로그 형식) | T1 감사 후 결정 항목 재검토 |
| 카테고리 2 데이터가 원본 ZIP에 없음 | T2에서 확인. 없으면 출처와 대체 경로를 보고하고 결정받음 |
| 웹 할당량 초과 | D-8 대체 경로로 다시 수집. 웹 결과를 섞지 않음 |
| 정답 그래프 누출 (Asia, Child, Sachs) | 사전 누출 규칙과 수집 후 검사. 제외 문서 기록 |
| LLM 사전 지식 오염 | 검색 없는 LLM 결과와 비교해 보고 (R8) |
| 실행 시간 초과 | G1에서 사례 수 사전 고정. 결과를 보고 줄이지 않음 |
| 4B 모델 한계로 상태 생성 품질 저하 | 개발 단계에서 실패 유형 기록. 모델 변경은 별도 결정 |
