## D01. 로그가 없는 pod에 어떤 정보를 제공할 것인가

관련 Task: 035, 024. **2026-09-25 B안 승인:** 사용자는 로그 쌍 불일치를 유지한 채 진행하도록 결정했다. pod 후보는 유지하고 부재를 명시하며 서비스/replica 로그로 대체하지 않는다. [구현 범위·검증·통합 경계](RCA_LOG_POLICY.md). 재시작/종료가 실제 누락 원인이라고 확정한 것은 아니며 UNKNOWN으로 기록한다. D01 정책 승인은 더 이상 대기 항목이 아니다.

**TASK_038 인터넷 조사 당시:** 같은 CC 20231207의 메트릭 pod 목록이 동일한 제3자 구현을 찾았지만 서비스 집계 방식이 달라 MATMCD의 누락 처리 근거로 채택하지 않았다. D01 직접 해결 이슈는 조사 범위에서 미발견이다. [출처와 판단 한계](D01_PUBLIC_CASE_RESEARCH.md). 조사 자체가 승인 근거였던 것은 아니며 이후 사용자의 명시적 결정으로 B안을 승인했다.

**TASK_037 후속 분석:** 사용자의 요청으로 파싱 오류 가능성을 다시 조사했다. 로컬 이름/경로 매칭에서 놓친 파일은 없었고, 공개 metric/log 범위 차이를 확인했다. 문제의 410개 pod는 배포 CSV 쌍이 둘 다 없지만 CC 원시 노드 로그에는 그중 3개의 언급이 있다. '로그 정보 자체가 없음'으로 해석하지 않는다. [상세 원인·조사 범위](D01_LOG_COVERAGE_ANALYSIS.md). 아래 B안은 임시 진행 선택지이며 필수 해결책으로 확정하지 않는다. 원본 최종 후보 목록과 처리 정책 확인을 우선하며, LEMMA 기준선의 교집합 처리를 MATMCD에 자동 적용하지 않는다.

최초 준비한 5개 사례의 metric 후보는 PR 208/207/218/228개와 CC 196개였다. 정확한 로그 쌍은 109/112/154/148/124개이며, 각각 99/95/64/80/72개에 대해 대응 파일 쌍이 없다. TASK_039의 현재 세 사례는 후보 642개·정확한 로그 426쌍·부재 216개이며 모두 기존 CSV에 남아 있다. 다른 폴더까지 동일 이름의 파일 쌍을 조사했지만 추가 매칭은 없었다. 이것은 원자료의 다른 형태에도 정보가 전혀 없다는 결론은 아니다.

문제는 단순 경로 누락이 아니다. 공개 generate_pod_summary는 pod별 파일 두 개가 있다고 가정하고 읽는다. 이후 DomainKnowledgeLLM은 비교하는 두 노드의 설명을 이름으로 직접 조회한다. 로그가 없는 노드의 설명을 어떻게 만들 것인지 원본 실행 지침에서 확인되지 않았다.

| 선택 | 구체적 처리 | 결과와 한계 |
|---|---|---|
| A. 완전한 저자 자료 우선 | 로그 또는 정확 매핑·누락 처리 지침을 확보할 때까지 해당 전체 로그 경로를 실행하지 않음 | 원본 충실성을 지키기 좋지만 자료 확보 시점은 불명. 독립 준비는 진행 가능 |
| **B. 모든 후보 유지 + 로그 부재 명시 (권장)** | 존재하는 로그만 요약하고, 없는 노드에는 사건·정상/비정상 판단을 생성하지 않은 부재 표시를 전달 | 원인 후보와 metric 입력은 유지. 추가 지식의 양이 pod별로 달라지며 저자 조건과의 동일성은 미확인 |
| C. 로그가 있는 pod만 사용 | 대응 로그가 없는 metric 열을 제거하고 전처리/그래프를 다시 구성 | 후보 수·조건부 독립·그래프·순위 난이도를 변경. 승인된 전처리 v1을 바꾸므로 권장하지 않음 |

B안의 구체적인 데이터 표시 제안:

```text
No matching log evidence is available for this pod in this case.
This does not imply normal operation or absence of causal influence.
```

이 표시는 가짜 로그나 정상 판정이 아니다. manifest에 evidence_available=false, 원인=exact_log_pair_unavailable을 남기고, 누락 pod에도 metric과 초기 그래프 기반의 기존 판단 경로를 유지한다. 누락을 이유로 노드·방향쌍을 건너뛰거나 정상으로 고정하지 않는다. 최종 요약이 누락 pod의 로그 사건을 새로 만들어 제공하지 않도록 해당 노드의 로그 근거 필드를 부재 표시로 고정한다. 시스템 요약에도 사용 가능한 로그 범위를 명시한다.

Latency는 pod가 아닌 입력 KPI 열이므로 pod 로그 부재와 별도로 구분한다. 열 이름·위치·입력 출처만 근거로 설명하고, pod 역할·사건을 만들지 않는다. PR 20220606의 KPI 의미 불확실성도 유지한다.

영향은 있다. 로그를 가진 pod와 없는 pod의 근거량이 다르므로 판단과 순위가 달라질 수 있다. 이후 비교할 MATMCD 기준선과 개선안에 동일한 원본 자료·부재 정책을 제공하고, 누락 비율 및 처리 내용을 결과에 함께 기록해야 한다. B안으로 원본과 같은 결과나 같은 개선 방향이 보장되는 것은 아니다.

**승인된 범위:** B안의 부재 표시 및 입력 완전성 검사 구현. 후보 제거·유사 이름 매핑·새 로그 생성·정답 자료의 모델 입력·다른 프롬프트/검색 변경은 포함하지 않는다. 기존 로그 요약 함수·프롬프트와 승인 모델을 사용한다. 실제 요약 실행은 읽기·길이 등 필요한 준비가 충족된 뒤 진행한다.

## D03. 그래프 방향·RWR의 논문/공개 코드 차이

관련 Task: 024, 018. 임의 교정을 하지 않았다.

후속 TASK_040에서 원본/논문을 대조하고 인공 입력으로 확인했다. 그래프 A[결과,원인]과 제약 C[원인,결과]의 차이 자체는 오류가 아니며 일괄 전치하지 않는다. **2026-09-26 사용자 선택은 A: 공개 동작 보존**이다. 그래프 설명·첫 질문 문장 재사용·첫 외부정보 없는 제약 보정(CC) 단계 RWR 입력을 유지한다. [채택 A/미적용 B의 차이](RCA_ORIGINAL_PROTOCOL_REVIEW.md), [저자 문의 준비](AUTHOR_QUESTIONS_D03_D04.md).

- 그래프를 설명하는 프롬프트는 행렬의 비영 [i,j]를 i→j로 서술하지만, 공개 시각화/변환 경로는 값 1을 j→i로 다룬다. -1/2 처리도 확인해야 한다. 이 차이는 모델이 받는 인과관계 설명을 바꾼다.
- 첫 방향쌍에서 만든 설명이 이후 쌍에도 재사용되는 부분이 있다. 단순 저장 경로 문제가 아니다.
- 첫 외부정보 없는 CC 보정 단계의 RWR만 초기 그래프를 재사용한다. 뒤의 추가정보/RE 단계는 보정 그래프를 사용한다. 따라서 이 RWR 문제를 모든 MATMCD 단계의 동일한 오류로 설명하지 않는다.

현재 기준선은 공개 동작을 보존한다. B는 미채택 대안으로 기록만 남겼다. 이후 교정을 선택한다면 새 프로필로 구분하고 비교 양쪽의 조건을 맞춰야 한다. 이번 A 승인으로 교정까지 허용된 것으로 해석하지 않는다.

CC의 두 후보는 productpage-v1-94d68db49-j7t55와 productpage-v1-94d68db49-vc8ct다. 공식 시나리오 4/5쪽은 한 replica에만 장애를 주입했다고 설명한다. 두 pod를 모두 정답으로 보고 더 높은 순위를 쓰거나 CPU가 더 큰 pod를 정답으로 선택하면 평가 가정이 새로 생긴다.

TASK_034에서 원자료 ZIP도 추가 확보하여 전후 pod 목록을 확인했다. j7t55는 이후 목록에서 사라지고 zvtz8가 등장한다. 이는 유력한 조사 단서이지만 주입 대상을 명시한 기록은 아니므로 정답으로 확정하지 않았다. 원자료와 전처리 자료의 영문 시나리오는 동일 파일이었다. [추가 조사와 한계](RCA_SCENARIO_EVIDENCE.md)를 참고한다.

정확한 주입 대상의 전체 이름을 추가 근거/저자에게 확인하는 것이 우선이다. 이름이 확정되지 않은 동안 예측 자체와 정답 평가를 분리할 수는 있지만, 한쪽을 임의 선택한 단일 성능 수치를 논문 재현 결과로 제출해서는 안 된다. 필요하면 두 가정별 결과를 별도로 보여주는 진단을 승인받아 할 수 있으며, 좋은 쪽만 채택하지 않는다.

공개 보조 코드의 PR 4개 날짜와 CC 1개 날짜가 표 4의 실제 집계 사례와 어떻게 대응하는지도 미확인이다. 기존 다섯 입력 준비를 다섯 사례의 동일 논문 집계 승인으로 확대하지 않는다. 후보 단위(pod/service), KPI의 후보 포함, 동점 순서, RWR 난수·반복·집계는 실제 실행/평가 프로토콜에 기록해야 한다. Qwen의 이미 승인한 seed와 RWR의 NumPy 난수 상태는 서로 다른 항목이다.

TASK_039로 현재 실행·평가 사례는 세 개로 확정됐다. 제외 사례를 집계에 포함하지 않는다. 위 잠정 정답·반복·집계 방침도 다시 승인받지 않는다. 저자 원조건과 CC 정확 정답은 후속 확인한다. 결과는 사용자 선택 부분집합의 로컬 비교로 표시하고 논문 표 4와 동일 조건이라고 주장하지 않는다.

## D05. 준비 로그의 문맥 용량 해결 — TASK_045

사용자가 문맥만 81,920으로 확대해 재검증하도록 지시했다. GPU all/FP16·전체 Pod·출력 8,192·모델/입력 조건을 유지해 278/278개 수용과 최대 입력 65,073토큰의 실제 생성에 성공했다(출력 807, client 60.57초). 준비 로그의 용량 문제는 해결했고 RAG/그래프·전체 통합은 미검증이다. 이번 요청의 검증 범위까지 수행했으며 전체 실험을 자동 시작하지 않는다. [검증 기록](../tasks/TASK_045_validate_context_81920.md).

### 이전 세 사례의 B안 선택 이력

전체 426개 로그 프롬프트 측정에서 최대 입력 131,003, 출력 포함 최소 139,196토큰을 확인했다. 초기 32,768안은 불충분하여 대체했다. 문맥 147,456·GPU 24개/나머지 CPU 배치안을 제시했으나 사용자는 B안(현재 설정 유지·실행 보류)을 선택했다. 원본 입력·모델·출력·FP16 캐시를 유지하고 새 배치는 적용하지 않았고 현재 16,384/all을 유지한다. 같은 변경 승인을 다시 묻거나 실제 실행을 자동 재개하지 않는다. [측정·구체안](RCA_CONTEXT_CAPACITY.md), TASK_042.

## D06. 원본 UTF-8 읽기 — A안 승인·적용 완료

원본 해시가 일치하는 일부 CSV가 기본 UTF-8 읽기에서 실패한다. 사용자는 실패 파일에만 surrogateescape로 바이트를 보존해 읽고, 이벤트 식별/선택 열 및 최종 프롬프트가 유효할 때만 사용하는 A안을 승인했다. 원본·최초 실패·모든 행·선택 규칙을 보존한다. 선택 결과에 오류가 남으면 별도로 보고하며 삭제·대체·Pod 제외로 우회하지 않는다. [영향·근거](RCA_LOG_ENCODING.md), TASK_043. 23쌍 모두 승인 조건을 통과해 기존 정상 403쌍과 합쳐 426쌍 전부 준비됐다. 저자의 실제 처리 방식은 미확정이다.
