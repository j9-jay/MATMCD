# 로컬 RCA 완주를 위한 자원 처리 변경안

**후속 지시가 아래 최초 제안보다 우선한다:** 사용자는 진행 승인 후 “일단 스크립트의 로직 변경이 있는건 제외하고 캐시 설정은 모두 셋팅해줘”로 범위를 좁혔다. 서버/요청의 prompt cache만 활성화하며 별도 RAM cache=0을 유지한다. PC 자료구조 최적화·중단 재개·실행 순서 변경은 적용하지 않는다. 아래 내용은 최초 구체안 이력이며 전체가 현재 승인된 구현 범위라는 뜻이 아니다. 결과는 [TASK_049](../tasks/TASK_049_local_resource_optimization.md)에 기록한다.

2026-09-26. 사용자가 유료 API/외부 서버를 제외하고 현재 PC에서 완료하도록 지시했다. 이 문서는 코드 조사에 근거한 **미승인 제안**이다. 실행 설정·공식 코드·설치 라이브러리는 변경하지 않았고 새 실험도 시작하지 않았다.

## 확인된 사실

- 현재 두 사례와 전체 후보(PR 218 Pod + KPI, CC 196 Pod + KPI)를 유지한다.
- PR 원본 PC 실행은 Depth 2에서 WSL OOM으로 종료됐다. 원인별 heap 측정은 없어 캐시만의 문제라고 단정할 수 없다. [기존 실패 기록](RCA_PC_MEMORY.md).
- 설치된 causal-learn 0.1.4.1의 `cit.py:73,168,180`은 FisherZ 검정값을 제한 없는 `pvalue_cache`에 저장한다.
- 같은 버전의 `SkeletonDiscovery.py:96-97,116-117`은 동일 간선을 조건 집합마다 `edge_removal`에 중복 추가하고, :130에서 마지막에 중복을 제거한다. 두 저장 구조 모두 메모리 증가 경로다.
- 로컬 `scripts/local_llm_client.py:34`는 `cache_prompt=False`, `scripts/local_llm_runtime.py:40`은 `--no-cache-prompt --cache-ram 0`이다. 요청과 서버 양쪽에서 공통 입력 계산의 재사용이 꺼져 있다. MATMCD DomainKnowledgeLLM은 같은 그래프 설명을 여러 방향쌍 프롬프트 앞부분에 반복한다.
- 고정 llama.cpp 문서는 prompt caching이 동일한 접두부의 KV 계산을 재사용한다고 설명한다. 다만 처리 배치 차이로 logits의 비트 단위 일치를 보장하지 않는다고 명시한다. [고정 버전 문서](https://github.com/ggml-org/llama.cpp/blob/7fe450e19305b828c199d602c23a8337aaa1f03b/tools/server/README.md).
- 캐시를 켜도 PR MATMCD 한 방법의 95,484회 호출은 그대로다. 출력 생성 비용, 깊은 PC 탐색의 계산량, 전체 그래프 프롬프트 길이와 RAG/파서 문제까지 해결된 것은 아니다.

## 제안 범위

### 1. PC 계산의 중간 저장량 제한

공식 파일과 site-packages를 보존하고, 명시적으로 선택하는 로컬 어댑터에서만 적용한다. 어댑터를 쓴 실행은 원본 코드 그대로 실행한 결과와 구분한다.

- FisherZ 계산식과 입력은 그대로 두고 p-value 캐시만 최근 100,000개 검정값을 저장하는 방식으로 바꾼다. 식별용 메타데이터는 별도로 유지한다. 제거한 값이 다시 필요하면 **원래 FisherZ 함수로 재계산**한다. 검정 생략·p-value 반올림·근사·디스크 swap 확대는 포함하지 않는다. 100,000은 로컬 자원 설정이며 논문 하이퍼파라미터가 아니다.
- `edge_removal`은 같은 방향 간선을 한 번만 저장하고 빠르게 포함 여부를 확인한다. 간선 제거 조건·검정 순서·sepset 수집·깊이별 제거 시점을 보존한다.
- 후보·행·메트릭·PC alpha/stable/깊이 종료 조건·배경 지식·RWR를 변경하지 않는다. 캐시 누락으로 재계산이 늘어 오히려 일부 구간이 느려질 수 있다.
- 먼저 강제 캐시 퇴출을 포함한 p-value 정확 일치, 초기/배경 지식 PC 그래프·sepset 대조를 수행한다. 제한된 검증 통과를 모든 입력에서의 동등성 증명이라고 부르지 않는다. 이후 전체 PR에서 peak RAM과 진행을 관측한다. 성공 여부와 완료 시간은 아직 미측정이다.

### 2. LLM의 공통 입력 계산 재사용 검증

- 동일 Qwen3.5-4B Q5_K_M, non-thinking, 문맥 81,920, FP16, GPU all, parallel=1, 원본 프롬프트, 기존 출력 한도·seed·온도·sampling을 유지한다.
- 별도 검증 프로필에서 서버 `--cache-prompt`와 요청 `cache_prompt=True`를 함께 사용한다. 처음에는 `--cache-ram 0`을 유지해 다중 요청의 RAM 캐시를 자동 확대하지 않는다. 슬롯 내부 접두부 재사용과 RAM에 여러 캐시를 보관하는 설정을 구분한다.
- 동일 입력의 캐시 꺼짐/켜짐을 대조하고, 서로 다른 두 질문에 공통 접두부가 있을 때 `cache_n`, `prompt_n`, prefill 시간, 생성 시간, RAM/VRAM, 실제 응답과 파서 성공 여부를 기록한다. 최종 PC 그래프가 아직 없으므로 그 전의 인공 그래프 검증은 성능 예비 검사로만 취급한다.
- Qwen의 혼합 구조에서 실제로 유효한 캐시 재사용이 일어나는지 확인하기 전 가속률을 주장하지 않는다. 실제 그래프/정보 프롬프트가 준비되면 대표 요청으로 다시 측정한다.
- **동일 seed에서도 생성 내용과 이후 RCA 순위가 달라질 수 있다.** 채택 시 추론 실행 방식 차이로 표시하고 전환 전후 결과를 같은 조건의 결과로 섞지 않는다. 파싱 성공은 의미 정확성 증명이 아니다.
- 속도 이득이 없거나 메모리 문제가 나면 성공 처리하지 않으며, 다른 캐시 크기·문맥·모델로 자동 전환하지 않는다.

### 3. 완료한 계산의 저장과 재개

- 그래프/각 LLM 응답/제약/순위를 단계별로 기록하고 재개 시 데이터·프롬프트·모델·설정·코드 식별자를 대조한다.
- 완료·검증된 동일 조건 산출물만 재사용한다. 다른 로그 프로필의 기존 148개를 새 44개와 섞지 않는다.
- 응답 미저장 요청은 성공으로 취급하지 않는다. 명시적 재개 때 원래 기록을 보존하고 새 시도를 구분한다. 실패 응답을 고르거나 버려서 성능을 높이지 않으며 숨긴 자동 재시도는 추가하지 않는다.
- 에이전트가 모든 긴 프롬프트를 메모리에 중복 보관하는 부분은 디스크 기록으로 분리할 수 있도록 검토한다. 질문·응답 순서/대응을 유지해야 하며 과학적 계산을 생략하지 않는다.
- 첫 결과는 PR의 PC 기준선과 MATMCD 최종 순위다. CC와 다른 방법은 삭제하지 않고 이후 실행한다. 전체 두 사례 완료로 미리 표시하지 않는다.

## 승인과 적용 기준

요청하는 승인은 위 **PC 중간 저장 구조 변경, LLM 캐시 사용 검증, 산출물 저장/재개와 첫 PR 결과 우선 실행**이다. 의미를 유지하려는 PC 구현 변경과 응답 차이가 가능한 LLM 실행 변경을 구분해 승인받는다. 검증 통과 후 승인 범위의 실행은 같은 승인을 반복 요청하지 않고 이어간다.

승인 전에는 조사 문서만 저장한다. 루트 AGENTS.md의 “원본 구현을 임의로 개선, 최적화, 현대화, 리팩터링하거나 다른 구현으로 대체하지 않는다”는 규칙 때문에 이 구현 변경은 별도 승인이 필요하다.

유료 API/클라우드, Pod/기간/행 축소, 프롬프트 합치기·요약·잘라내기, PC 깊이 제한, 모델 교체, 추가 샘플링 변경은 포함하지 않는다. 이 안의 전체 완료 시간은 아직 보장할 수 없다. 효과를 실측한 뒤 다음 단계의 시간을 산정한다.

## 이번 조사 결과

코드와 고정 문서에서 구체적인 최적화 지점을 확인했다. 자원 적합성/수치 동등성/전체 실행 검증은 미실시다. 따라서 “PC 사양상 무조건 불가능”, “캐시만 켜면 반드시 완주” 어느 쪽도 현재 근거로 단정하지 않는다. 신규 Windows CIM 사양 조회는 권한 오류였으며 기존 환경 기록을 현재 재측정값으로 표시하지 않았다.
