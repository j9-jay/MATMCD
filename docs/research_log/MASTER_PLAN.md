- 학생이 "왜 잘 됐는지 모르는 것", "스스로 실험을 의심하는 것" 두 가지를 우려했다.

### 1.3 이 계획이 생긴 이유 (사용자가 진단한 근본 문제)
- 지금까지는 AI가 개발용 데이터의 결과를 보며 방법을 반복 수정했다.

- 해결: 설계 과정을 가장 중요하고 가장 오래 걸리는 단계로 두고, 모든 선택을 사용자가 하며, 상세히 기록한다.

## 3. 작업 규칙 (구속력 있음)

### R1. 사용자가 모든 선택을 한다
- AI가 혼자 하는 일은 **이미 승인된 작업의 단순 실행**뿐이다 (승인된 명세대로 코드 작성, 승인된 실험 실행, 파일 읽기, 기록 정리).
- 실행 중 새로운 선택이 생기면 즉시 멈추고 후보를 제시한다. 임의로 정하고 넘어가지 않는다.
- 해석이 갈리는 사실 판단(예: 재현 차이의 원인, 논문 포함 여부)도 근거와 후보 해석을 제시하고 사용자가 판단한다.

### R2. 답안지를 보지 않는다
- 금지: 실험 점수나 사례별 정답 여부를 보고 방법(프롬프트, 구조, 설정값, 로직)을 고치는 것.
- 금지: 결과를 보고 더 나은 설정을 찾아 다시 실행하는 것.
- 금지: 명세서 작성 중 평가 데이터의 사례나 MATMCD 실패 사례를 들여다보는 것.
- 설계 근거로 쓸 수 있는 것: 사용자의 원래 아이디어, 논문, RCA 일반 지식, 데이터셋 문서에 공개된 형식 정보.
- 허용: ablation(방법을 고치지 않고 요소를 빼서 분석), 동결 이후의 실패 사례 분석(설명 목적, 방법에 반영하지 않음).

### R3. 설계 → 구현 → 동결 → 한 번 실행
- 명세서와 코드를 커밋한 해시가 동결 시점이다. 이후 방법을 고치지 않는다.
- 결과가 나빠도 그대로 보고하고 원인만 분석한다.
- 결과를 본 뒤 떠오른 아이디어는 이번 결과에 반영하지 않고 "다음 버전 후보"로 따로 기록한다. 다음 버전은 보지 않은 데이터로 평가하거나 "탐색적"이라고 명시한다.

### R4. 버그 판정
- 버그로 인정: 코드가 **동결된 명세서와 다르게** 동작한 경우만.
- 버그 아님: 명세서대로 동작했는데 결과가 나쁜 경우. 고치지 않는다.
- 버그 수정 시: 무엇이 명세서와 달랐는지 기록 → 사용자 승인 → 본 실험과 ablation 전체 재실행 → 버그가 있던 결과도 보존.

### R5. 숫자 설정값
명세서의 숫자 하나하나에 아래 우선순위를 적용하고, 어느 단계로 정했는지 표시한다.
1. 숫자가 필요 없는 구조로 바꾼다.
2. 원리적 기본값 (예: 전부 사용, 같은 비중).
3. 다른 논문이나 도구의 값 (출처 명시).
4. 그래도 남으면 "임의로 정함"이라고 명시한다.
결과를 보고 정한 값은 있어서는 안 된다. v0에서 결과를 보고 정한 값을 새 명세서로 옮기지 않는다.

### R6. 기록
- 설계 결정 하나당 기록 파일 하나 (5절 양식).
- 가설, 사전 예측, 결정, 설명은 **사용자가 쓴다**. AI는 대신 쓰지 않는다.
- 근거가 없으면 "근거 없음"이라고 쓴다. 그럴듯한 이유를 지어내지 않는다.
- 설명은 요약하지 않는다. 실제 원문, 숫자, 출처를 붙이고 단계를 생략하지 않는다.

### R7. 서브에이전트
- 하는 일: 문헌 조사, 승인된 명세대로 실험 실행, 결과 수집.
- 하지 않는 일: 방법 수정, 설정 탐색, 결과 해석, 선택.

### R8. 재현과 보존 (AGENTS.md)
- MATMCD 재현 실험은 하지 않는다(K12). 논문의 수치는 논문에 적힌 그대로 인용하고, 논문의 실험 조건을 추측해 채우지 않는다.
- 기존 결과 파일을 지우거나 덮어쓰지 않는다.
- 파일을 만들거나 바꾸기 전에 무엇을 왜 바꾸는지 사용자에게 알린다.
- 범위를 줄이는 것(일부 사례만, 상한 설정)은 사전에 제안하고 승인받는다. 앞에서부터 N개 같은 부분집합은 쓰지 않는다.

## 4. 후보 제시 형식 (R1, K10)

한 번에 결정 하나만 다룬다. 사용자가 선택하고 이유를 적기 전에는 다음 결정으로 넘어가지 않는다.

### 4.1 방법의 동작에 영향을 주는 결정
(예: 검색 방식, state 구성, RCA 답 생성 방식, 프롬프트 구조, 입력 정보, 모델 호출 방식)

1. **결정할 것**: 무엇을 정해야 하고 왜 지금 필요한가.
2. **전체 구조에서의 위치**: 파이프라인 다이어그램에 이 결정의 위치를 표시.
3. **후보 2~4개**, 각 후보마다:
   - 다이어그램 (데이터 흐름)
   - 수도 코드 또는 짧은 샘플 코드
   - 작은 가상 예시 (평가 데이터 사용 금지): 입력이 각 단계에서 무엇이 되는지
   - 논리: 왜 문제를 해결할 것으로 기대되는지, 단계별로
   - 제안한 이유와 근거: 왜 후보에 넣었는지, 어떤 논문·기존 방법에 근거하는지 (출처). 근거가 없으면 "근거 없음, AI의 추론"이라고 표시
4. **비교표**: 장점, 단점, 교수님께 한 문장 설명 가능 여부, 새로 생기는 숫자와 그 근거 가능성(R5), ablation으로 깔끔하게 뺄 수 있는지, 공정성(MATMCD와 입력·비용 차이), 구현·실행 비용.
5. **AI 의견**: 분리해서 표시. U3에서 사용자가 원하지 않으면 생략.
6. **사용자 선택과 기록**: 고른 후보, 이유, 버린 후보와 버린 이유 (사용자 작성).
7. **이해 확인(teach-back)**: 사용자가 선택한 방식을 자기 말로 설명하고, AI가 교수님처럼 "왜?", "다른 방법은?", "근거는?"을 묻는다. 막히면 그 결정은 완료가 아니다.

### 4.2 동작에 영향이 없는 결정
(예: 파일·함수 구성, 로그 형식, 결과 저장 위치)
- 항목마다 후보와 차이를 간단한 표로 제시하고 사용자가 선택한다. 형식은 간단해도 선택은 사용자가 한다.
- 어느 쪽인지 애매하면 4.1로 다룬다.

## 10. 하지 말아야 할 일 (이어받는 AI용 요약)

1. 사용자 대신 선택하지 않는다. "합리적 기본값"으로 채우고 넘어가지 않는다.
2. 점수를 보고 코드를 고치지 않는다. 더 좋은 점수를 얻으려고 다시 돌리지 않는다.
3. 명세서 작성 중에 평가 데이터 사례를 열어 보지 않는다.
4. 가설, 예측, 결정 이유, 설명을 대신 써 주지 않는다.
5. v0에서 결과를 보고 정한 값을 새 방법으로 가져오지 않는다.
6. MATMCD 재현을 다시 시도하지 않는다. 기존 재현 결과를 비교나 보고에 쓰지 않는다. MATMCD는 논문의 공식 수치만 인용한다.
7. 기존 결과를 지우거나 덮어쓰지 않는다.
8. 서브에이전트에게 해석이나 선택을 맡기지 않는다.
9. 설명을 요약으로 대신하지 않는다. 실제 원문, 숫자, 출처를 붙인다.
10. upstream에 push하지 않는다. 변경은 origin PR로 남긴다.
