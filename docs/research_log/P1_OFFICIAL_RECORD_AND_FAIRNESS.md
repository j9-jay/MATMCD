## 0. 요약

1. MATMCD의 공식 RCA 기록은 표 4 하나이고, **사례는 2개**(Product Review 1개, Cloud Computing 1개)다. 지표는 그 두 사례의 정답 순위에서 계산한 값이다.
2. **공식 지표 계산은 논문의 수식과 공식 코드가 다르다.** 표 4의 숫자는 공식 코드의 계산(`rank < K`)과 일치한다. 이 계산에서는 정답이 1위여도 MAP@5가 0.8이다.

5. 논문은 무관한 Pod를 걸러냈는데 **규칙, 남은 후보 수, 목록이 모두 공개되지 않았다.** K14(걸러내지 않음)는 논문보다 후보가 많은 조건이 된다.
6. 과거 기록의 "LEMMA-RCA는 이 PC에서 불가능"이라는 판단의 근거는 대부분 **MATMCD 방식에 고유한 제약**(전체 Pod에 대한 PC 알고리즘의 메모리, Pod 쌍마다의 LLM 호출 약 52만 회)이다. 데이터 자체의 제약은 로그 용량(두 사례 8.81GB), 로그 없는 Pod, 정답 라벨 문제다.

## 2. P1-T2 지표의 정의와 계산

### 2.1 논문 부록 B.2의 정의 (확인됨)
- PR@K: 상위 K개 예측 안에 정답이 들어 있는 비율.
- MAP@K: j = 1부터 K까지의 PR@j를 평균한 값.
- MRR: 정답 순위의 역수를 사례에 대해 평균한 값.

### 2.2 공식 코드의 계산 (확인됨, 출처: `official/matmcd/LEMMA_Metrics.py`)

```python
def PRK(K, A, rank_list):
    true_number = 0
    for rank in rank_list:
        if rank < K:          # "이하"가 아니라 "미만"
            true_number += 1
    return true_number / A

def MAPK(K, A, rank_list):
    result = 0
    for k in range(1, K + 1):
        result += PRK(k, A, rank_list)
    return result / K

def MRR(rank_list):
    return sum(1 / rank for rank in rank_list) / len(rank_list)
```

- 이 파일은 실험 출력을 읽지 않는다. 코드 안에 적힌 고정 순위 목록(예: MATMCD `[2, 7]`, PC `[5, 13]`)을 집계할 뿐이다.

### 2.3 표 4와의 대조 (확인됨, 직접 계산)

정답이 사례마다 1개이고 사례가 2개일 때, 공식 코드의 계산은 다음과 같다.

MAP@K = 사례별 max(K − 순위, 0) / K 의 평균

| 방법 | 순위 | MAP@5 계산 | MAP@10 계산 | MRR 계산 | 표 4 |
|---|---|---|---|---|---|
| MATMCD | 2, 7 | (3/5 + 0/5) / 2 = 0.30 | (8/10 + 3/10) / 2 = 0.55 | (1/2 + 1/7) / 2 = 0.321 | 30.0%, 55.0%, 0.32 일치 |
| PC | 5, 13 | (0 + 0) / 2 = 0 | (5/10 + 0) / 2 = 0.25 | (1/5 + 1/13) / 2 = 0.138 | 0.0%, 25.0%, 0.14 일치 |

- 순위 "이하"로 계산하면 MATMCD의 MAP@5는 0.40이 되어 표 4(30.0%)와 맞지 않는다. 표 4는 공식 코드의 "미만" 계산으로 만들어졌다.
- **이 계산의 성질**: 정답이 1위여도 MAP@5는 0.8, MAP@10은 0.9다. 두 사례 모두 1위일 때의 최댓값이 MAP@5 80%, MAP@10 90%, MRR 1.0이다. 5위면 MAP@5에 기여가 0이다.
- 출처 대조: `docs/RCA_METRIC_ADAPTER.md`, `docs/RCA_ORIGINAL_PROTOCOL_REVIEW.md` 55행.

### 2.4 순위를 매기는 대상 (확인됨, 출처: RCA_ORIGINAL_PROTOCOL_REVIEW.md 43-51행)
- 공식 코드는 KPI(Latency) 열을 순위 목록에서 빼지 않는다. 즉 순위는 "모든 Pod + KPI"에 대해 매겨진다.
- 동점은 입력 열 순서대로 처리한다.

- 슬라이드 5: "Affected pods: productpage-v1 one system", 측정 기간 2023/12/06 18:45 ~ 2023/12/08 17:00 (JST), CPU 부하 증가 2023/12/07 16:48 (JST)
- README: 슬라이드 시각은 일본 표준시(JST), 데이터는 UTC. 9시간 차이.
- **장애를 넣은 Pod의 전체 이름(접미어)은 어느 문서에도 없다.**

**간접 단서 (추정, 확정 근거 아님)**
1. Pod 목록의 변화: 측정 전 목록(`all_pod_before.txt`)에는 `productpage-v1-94d68db49-j7t55`와 `-vc8ct`가 있다. 측정 후 목록(`all_pod_after.txt`)에는 `-vc8ct`(나이 2일)와 새 Pod `-zvtz8`(나이 7시간 59분)이 있고 `-j7t55`가 없다. 측정 중이나 후에 `j7t55`가 교체됐다. 장애 Pod가 교체된 것일 수 있으나, 다른 이유(노드 교체 등)일 수도 있다.
2. 슬라이드 3의 구성도: 장애 Pod가 세 번째 가용 영역의 맨 오른쪽 노드에 그려져 있다. 그러나 그림은 개념도이고, 그림의 가용 영역과 실제 노드(`j7t55`는 `ip-10-1-64-27`, `vc8ct`는 `ip-10-1-32-15`)를 잇는 정보가 없다. 판단에 쓸 수 없다.

**새로 발견한 점 (확인됨)**
- 측정 전 목록에는 `test` 네임스페이스에 `productpage-v1-7f4c6b8f9-6vmpx`라는 세 번째 Pod도 있다. 이름이 `productpage-v1`로 시작한다.
- 공식 정답 표기 `productpage-v1`을 접두어로 맞추면 이 Pod도 걸린다. 장애 대상은 `book-info` 네임스페이스(슬라이드 4 "Fault Target Microservice book-info")이므로 이 Pod는 정답이 아니다.
- 과거 기록은 후보를 2개로 적었다. 과거 임시 전처리 입력에 이 Pod가 빠져 있었는지는 이번에 확인하지 않았다. K14(걸러내지 않음)로 Pod 전체를 후보로 두면 이 Pod가 후보에 들어올 수 있어, 정답 판정 규칙에 네임스페이스를 포함해야 한다.

**결론**: 공개 문서로는 두 복제본 중 어느 쪽인지 확정할 수 없다. G1-B는 여전히 사용자 결정이 필요하다.

**G1-B 결정 (2026-11-18, MASTER_PLAN K16)**: 주 점수는 두 복제본 중 먼저 나온 순위(후보 A), 보조로 두 가정의 순위를 함께 적는다(후보 C). 정답 판정은 `book-info` 네임스페이스까지 맞아야 한다. 결정적 증거가 나오면 그때 반영한다.

### 6.1 "같은 표에 놓을 수 있는가"에 대한 사실 정리
- 같은 것: 데이터셋(LEMMA-RCA), 지표 계산식, 정답 표기의 출처(공식 보조 코드).
- 다를 수 있는 것: PR의 날짜(미공개), 후보 범위(논문은 필터 후, K14는 전체), LLM(논문 GPT-4o mini), 입력 전처리(저자 CSV 미공개), 정답 Pod의 정확한 대응(CC 미확정).
- 사례가 2개뿐이다. 순위 한 칸의 차이가 MAP@10을 5%p 움직인다(예: 한 사례에서 2위와 3위의 차이는 (8−7)/10/2 = 0.05).
