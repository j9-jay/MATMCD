실험 계획

핵심 가설과 개선하려는 부분 추가

가설: LLM이 장애 원인을 판단할 때, 질의 하나로 근거를 한꺼번에 찾는 대신(flat RAG) 지금 추론 단계에 필요한 종류의 근거를 단계별로 골라 주면, 판단에 핵심인 근거를 더 많이 찾고 최종 판단도 좋아진다.

개선하려는 부분: 텔레메트리(숫자 위주)와 시스템 문서(긴 문장)가 섞인 근거 풀에서는 유사도 검색이 문서 쪽으로 쏠려 판단에 필요한 이상 신호를 놓칩니다.

MATMCD 재현 실험

  • RCA: MATMCD 방식(DA-agent 웹 검색 → CC-agent 쌍별 판단 → PC → RWR)을 RE2-OB 30사례에 참고 기준선으로 실행.
  • 인과 발견: 논문 벤치마크 5종(AutoMPG, DWD, Sachs, Asia, Child)에서 변수 쌍마다 인과 관계를 판단해 그래프를 만들고 정답 그래프와 비교.

내 실험 시나리오

  • 같은 근거 풀, 같은 LLM, 같은 판단 프롬프트를 쓰고 근거를 고르는 방식만 바꿉니다.
  • 비교 대상: none(근거 없음), flat(유사도 검색), role_only(근거 종류만 나눔), state_fixed(제안), state_dynamic(참고: LLM이 가설 수립), MATMCD(참고).

인과 발견 벤치마크 5종: 데이터 예시

각 데이터는 변수 여러 개의 관측값 표와 전문가(또는 베이지안 네트워크)가 정한 정답 인과 그래프로 이루어집니다. 방법은 변수 쌍마다 "A가 바뀌면 B가 바뀌는가?"를 판단해 그래프를 만들고, 정답 그래프와 비교합니다.

2.1 아이디어와 구현

장애 분석을 하는 사람은 "무슨 증상이 있나 → 시스템이 어떻게 연결돼 있나 → 어떤 서비스의 어떤 문제일까 → 그 가설의 증거는?" 순서로 생각합니다. 이 순서를 근거 검색의 단계(추론 상태)로 만들었습니다.

select_state_fixed(case, K=24):
  strength  = 서비스별 이상 표시 분(min) 합            # 정답 미사용
  suspects  = strength 상위 3개 서비스
  S1 텔레메트리 (7):  KPI 1 + 의심 서비스별 대표 이상 메트릭 + trace 오류
  S2 시스템 구조 (5): 의심 서비스의 호출 그래프 2 + 위키 03·04·07·10 중 3
  S3 가설:            (서비스, 메커니즘)  # 메커니즘 = S1 메트릭 종류
                      cpu·mem·diskio·socket·latency·workload·error
  S4 가설별 근거 (12): 가설마다 이상 표시 메트릭·trace 오류 우선
                      + 로그·trace + 메커니즘에 맞는 위키 문서
                      (예: memory → 위키 18·14·19, errors → 11·5·6·24)
  Fill:               남은 자리는 flat 질의로 채움
  return S1 + S2 + S4 + Fill  → 판단 LLM이 후보 서비스 순위 출력

  1. 텔레메트리와 시스템 문서가 섞인 근거 풀에서, 추론 상태에 맞춰 근거 종류와 대상 서비스를 고르면 핵심 근거 재현율이 flat 0에서 0.96으로 오르고, 판단 LLM이 그 근거를 인용합니다(출력부 B, 30사례).
  2. 이 효과는 LLM 호출을 늘리지 않는 규칙 기반 선택으로 얻었습니다(사례당 3호출).
  3. 저장소 정적 분석으로 사실마다 원본 출처를 단 운영 문서를 만드는 재현 가능한 방법을 제시했습니다(25문서, 출처 검증기).
