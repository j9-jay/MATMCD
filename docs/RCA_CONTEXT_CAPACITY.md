최대 요청: 입력 65,073토큰 → 출력 807토큰, client 약 60.57초, finish_reason=stop, 잘림 없음. GPU 전체 점유 표본 최대 6,481MiB, 최소 여유 1,507MiB, swap 사용 0. 서버 로그의 FP16 KV는 2,560MiB이고 33/33 레이어를 GPU에 배치했다. 현재 PC에서 이 요청은 성공했으므로 준비 로그 입력의 문맥 부족을 현재 Blocker로 유지하지 않는다.

RAG·그래프/제약·전체 RCA 통합 검증은 남아 있다. 이후 요청도 호출 직전 길이를 검사한다. 실제 전체 실험은 실행하지 않았고 설정은 검증된 81,920/all을 유지한다. 아래는 확대 전 제안 및 이전 3사례 측정 이력이다.

## 확대 전 산출·제안 — TASK_044의 두 사례

사용자가 PR 20211203과 CC 20231207만 실행·평가하도록 변경했다. 기존 프롬프트/모델/설정은 그대로이며 준비본의 출처·해시와 기존 토큰 측정의 입력 해시가 일치함을 확인했다. 재생성·재토큰화·LLM 호출 없이 선택한 사례의 실측을 추렸다. [범위 검사](evidence/rca_two_case_scope_20260926T075701648365Z.json).

| 사례 | 프롬프트 수 | 최대 입력 | 출력 8,192 + 여유 1 포함 | 현재 16,384 초과 |
|---|---:|---:|---:|---:|
| PR 20211203 | 154 | 65,073 | 73,266 | 88 |
| CC 20231207 | 124 | 63,304 | 71,497 | 36 |
| 합계/최대 | 278 | 65,073 | 73,266 | 124 |

새 권장 검증안은 **server.context_tokens: 16384 → 81920 한 항목 변경**이다. gpu_layers=all, Qwen GGUF, non-thinking, FP16 K/V 캐시, batch/microbatch, 출력 8192, seed/sampling, 원본 입력과 선택 규칙을 유지한다. 81,920은 최소 필요량 73,266을 16,384 단위로 올린 로컬 용량 선택이다. 이후 RAG/그래프 입력 길이는 아직 미확인이므로 같은 호출 직전 검사를 유지한다.

현재 실측 FP16 KV 512MiB의 5배인 2,560MiB(2.5GiB)가 필요할 것으로 계산된다. 주요 GPU 버퍼는 모델 2,987.56 + KV 2,560 + recurrent 50.25 + compute 20 = 약 5,617.81MiB다. 재부팅 후 GPU 전체 점유 표본 최대 4,253MiB에 캐시 증가분 2,048MiB만 더하면 약 6,301MiB다. **이는 참고 추정이며 긴 문맥의 실제 할당·추론 peak·품질·속도 검증은 아니다.**

검증 단계는 기존 설정 보존 → 승인된 경우 문맥만 81,920으로 변경 → 서버 로드·RAM/VRAM·278개 입력 수용 확인 → 최대 입력의 실제 생성/시간·응답 형식 확인이다. 실패 시 CPU 배치·캐시 정밀도·출력/입력을 자동 변경하지 않는다. 전체 RCA 실행은 준비 완료 및 실행 보류 해제 이후의 별도 단계다.

**현재 설정은 여전히 16,384/all이며 새 검증안은 미적용이다.** 이전 147,456/24안은 아래 3사례 이력으로 보존하고 현재 후보로 자동 적용하지 않는다. 실행·평가 범위만 두 사례로 변경됐다.

## 현재 PC와 메모리 근거

PC 재확인: AMD Ryzen 7 5700X3D 8코어/16스레드, 물리 RAM 17,083,305,984바이트(약 15.91GiB), RTX 2080 SUPER 8GiB. WSL MemTotal은 8,081,052KiB(약 7.71GiB), 측정 당시 MemAvailable 7,394,432KiB(약 7.05GiB)였다. OS/WSL 설정은 바꾸지 않았다.

고정 서버의 현재 실행 로그: GPU 모델 버퍼 2,987.56MiB, FP16 KV 512MiB, recurrent 상태 50.25MiB, compute 20MiB. 로그의 모델 metadata는 n_ctx_train=262144이며, 이것은 긴 문맥에서의 응답 품질 보장이 아니다. GPU 총 메모리는 8191MiB, 현재 실행 종료 직전 self 3569MiB·그 외 점유 1114MiB였다.

동일 FP16 KV를 모든 레이어에서 GPU에 유지하면 문맥 147,456은 현재의 9배이므로 KV만 약 4,608MiB다. 모델/상태/compute/기존 다른 점유를 더하면 약 8,780MiB로 계산되어 8GiB를 초과한다. **이는 현재 실측에 근거한 용량 추정이며 새 설정을 실제 구동한 결과는 아니다.**

## 권장 A — 같은 모델과 정밀도, 긴 문맥과 일부 CPU 배치 검증

승인받을 실제 설정 변경은 다음 두 항목이다.

| configs/local_llm.json 항목 | 현재 | 제안 |
|---|---|---|
| server.context_tokens | 16384 | 147456 |
| server.gpu_layers | all | 24 |

147,456은 측정된 최소 139,196을 16,384 단위로 올림한 로컬 용량 선택이다. 24개 GPU 레이어와 나머지 CPU 배치는 VRAM 여유를 확보하기 위한 **첫 검증 후보**이며 저자 설정이나 실측 완료값이 아니다. 정확한 GPU/CPU 버퍼 분배는 서버 로그로 확인한다. 이 CLI는 GPU에 둘 레이어 수를 명시할 수 있다. [고정 llama.cpp 설명](https://github.com/ggml-org/llama.cpp/blob/7fe450e19305b828c199d602c23a8337aaa1f03b/tools/server/README.md).

유지 범위: Qwen3.5-4B Q5_K_M의 동일 파일/해시·non-thinking·FP16 KV·기존 출력 8192·seed/sampling·원본 단계별 온도·batch/microbatch·입력과 예시 선택·D01~D04. KV 양자화·출력 축소·데이터/Pod 축소·모델 교체는 하지 않는다. fit=off와 문맥 자동 이동 금지도 유지한다.

검증 순서: 기존 설정과 증거 보존 → 두 설정만 변경 → 서버 시작과 실제 RAM/VRAM 배치 확인 → 426개 입력 수용 재확인 → 실제 생성 포함 통합 검증. 먼저 용량 검증을 마치며 시작/메모리 실패 시 다른 레이어 수·캐시 정밀도·모델로 자동 전환하지 않는다. 이후 실제 생성/그래프에서도 실패를 보존한다. 준비가 충족되면 기존의 조건부 실행 요청에 따라 실제 RCA로 진행한다.

영향: CPU 처리와 긴 입력 때문에 속도가 저하될 수 있다. 하드웨어 배치 차이는 같은 seed에서도 수치/생성 결과의 완전한 동일성을 보장하지 않는다. 4B 모델의 13만 토큰 입력 처리 품질·추론 시간은 아직 미측정이다. 현재 전체 방향쌍의 831,396회 호출 규모는 그대로이며, 실제 전체 실험의 소요 시간을 아직 약속할 수 없다. [호출 규모와 코드](LOCAL_RCA_RUNTIME.md).

## 대안 B — 설정 유지·해당 실행 보류

현재 16,384·GPU 전체 배치를 유지하면 207개 필수 로그 프롬프트가 수용되지 않아 세 사례의 전체 실행을 시작할 수 없다. 출력만 줄여도 입력 자체가 초과하는 파일은 해결되지 않는다. 추후 다른 하드웨어/원본 API를 별도 검토할 수 있으나 이번에 자동 전환하거나 과금 API를 호출하지 않는다.

사용자가 최종적으로 B안을 선택했다. 현재 context 16,384·gpu_layers all을 유지하고 실제 RCA 실행을 보류한다. A안은 검토 이력이며 승인 대기가 아니다. 실행 프로필은 BLOCKED_CAPACITY_USER_HOLD로 기록했다. 승인된 D06 처리는 완료됐으며 같은 결정을 다시 묻지 않는다. 모델/프롬프트를 임의 변경하지 말라는 사용자 지시에 따라 이번 문맥·실행 배치 선택을 별도 결정으로 제시한다.
