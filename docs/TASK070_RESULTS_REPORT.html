추론 상태 기반 근거 검색 실험: 처음부터 끝까지

이 실험이 무엇을 묻는지, 어떤 데이터로 어떤 장치를 만들었는지, 각 단계에서 무엇이 실제로 일어났는지, 그래서 어떤 결과가 나왔는지를 순서대로 모두 적었습니다. 실제 실행 기록에서 사례를 꺼내 입력부터 채점까지 따라가 보는 장도 있습니다. 앞에서부터 읽으면 뒤의 내용이 모두 이해되도록 썼습니다.

0이 문서 읽는 법과 한 문단 요약

읽는 순서. 1장은 이 실험이 어디서 출발했는지, 2장은 무엇을 시험하는지입니다. 3~7장은 실험 장치(데이터, 근거, 방법, 판단, 채점)를 하나씩 뜯어서 설명합니다. 8장은 실제로 일이 진행된 순서, 9장은 실제 사례 하나를 처음부터 끝까지 따라가는 장입니다. 10~12장이 결과와 해석과 한계이고, 13장은 교수님께 설명할 때 쓸 수 있는 요약입니다. 처음 보는 용어는 처음 나올 때 설명하고, 15장 용어집에도 모았습니다.

한 문단 요약

먼저 읽어 주세요 (2026-10-27 최종 갱신). RCA 실험의 최종 결과는 0-2장 v3입니다. 그보다 앞선 RCA 실험 v1(1~15장)과 v2(0-1장)는 무효입니다. 사용자 계획서가 근거 풀에 요구한 시스템 구조 문서가 빠진 채 진행했기 때문입니다. 두 장은 경위 기록으로만 남깁니다. 인과 발견(카테고리 2)은 위키 대상이 아니므로 0-1장의 v2 결과를 보조로 유지합니다. 아래 요약은 무효인 v1 기준입니다.

LLM에게 "어느 서비스가 장애의 원인인가", "변수 A가 변수 B의 원인인가"를 판단시키면서, 판단에 쓸 근거를 두 가지 방식으로 골라 넣었습니다. 하나는 질문 하나로 비슷한 근거를 한꺼번에 고르는 flat RAG, 다른 하나는 판단 과정을 "구조 확인 → 원인 쪽 이상 확인 → 시간 순서 확인"처럼 추론 상태로 나누고 상태마다 맞는 근거를 고르는 제안 방법입니다. 같은 LLM, 같은 근거 풀, 같은 질문으로 비교했고, 방법과 평가 사례는 결과를 보기 전에 고정했습니다. 그 결과 제안 방법은 정답과 관련된 근거를 1.5~1.7배 더 많이 골라 왔지만, 최종 판단은 flat RAG보다 유의하게 낫지 않았습니다(주 평가 Avg@5 0.848 대 0.825, p=0.76). 계획 기능을 뺀 단순한 변형이 오히려 더 좋았고, 개발 단계에서 보였던 큰 우위(0.94 대 0.78)는 평가에서 사라졌습니다.

0-2v3 재실험: 계획서대로 근거 풀을 갖춘 최종 RCA 실험

왜 다시 했나

사용자 연구 계획서는 근거 풀에 텔레메트리(메트릭·로그·trace)뿐 아니라 시스템 구조 문서(서비스 topology, dependency, architecture document)를 넣도록 되어 있었습니다. 상태 흐름도 "텔레메트리 → 시스템 구조 → 가설 → 가설별 근거 → 원인"이었습니다. v1과 v2는 이 문서 없이 텔레메트리만으로 진행했으므로 계획된 실험이 아니었고, 무효로 처리합니다.

1출발점: MATMCD와 첫 시도

1.1 MATMCD 논문이 한 일

MATMCD는 "LLM 에이전트 여러 개로 인과 그래프를 더 정확하게 찾는" 방법을 제안한 논문입니다. 인과 그래프란 변수 사이에 "원인 → 결과" 화살표를 그린 그림입니다. 예를 들어 흡연 → 폐암, 엔진 배기량 → 연비 같은 화살표들입니다.

데이터만 보고 이런 그래프를 찾는 통계 알고리즘(대표적으로 PC 알고리즘, 3장과 6장에서 설명)이 있지만, 데이터만으로는 화살표 방향을 정하기 어렵거나 틀리는 경우가 많습니다. MATMCD는 여기에 LLM의 상식과 외부 정보를 더합니다.

flowchart LR
  D[관측 데이터] --> PC1[PC 알고리즘: 초기 그래프]
  W[웹 검색 / 시스템 로그] --> DA[DA-AGENT: 정보를 찾아 요약]
  DA --> CC[CC-AGENT: 변수 쌍마다 인과 여부 판단]
  PC1 --> CC
  CC -->|이 화살표는 있다 / 없다| PC2[PC 알고리즘 다시 실행]
  PC2 --> G[최종 인과 그래프]
  • DA-AGENT(Data Augmentation Agent): 웹을 검색하거나 시스템 로그를 읽어서 각 변수가 무엇인지, 서로 어떤 관계인지 요약합니다.
  • CC-AGENT(Causal Constraint Agent): 그 요약을 근거로 변수 쌍마다 "A가 B의 원인인가"를 판단합니다.
  • 판단 결과를 "이 화살표는 반드시 있다(필수)", "이 화살표는 없다(금지)"라는 제약으로 바꿔 PC 알고리즘에 넣고 그래프를 다시 찾습니다.

논문은 이것을 두 종류 문제에 적용했습니다. (1) 인과 발견 벤치마크 5종(자동차 연비, 기후, 세포 신호, 폐질환, 신생아 질환)과 (2) 마이크로서비스 장애 원인 분석(LEMMA-RCA 데이터)입니다. 장애 분석에서는 그래프를 찾은 뒤 "증상이 나타난 곳에서 거꾸로 거슬러 올라가 원인을 찾는" 방법(RWR, 6장)으로 원인 순위를 매깁니다.

1.2 우리가 처음 한 일: LEMMA-RCA에서 MATMCD 재현

처음 목표는 MATMCD를 논문 그대로 재현하는 것이었습니다(TASK_050~053). LEMMA-RCA는 실제 시스템(상품 리뷰 시스템, 클라우드 컴퓨팅 시스템)에서 수집한 장애 데이터로, Pod(컨테이너 실행 단위)가 수백 개 있습니다. 모든 Pod를 후보로 넣으면 LLM 판단 쌍이 너무 많아지므로 후보를 30개로 줄여 재현했고, 재현 자체는 완료했습니다.

문제는 그 30개 후보 안에 정답 Pod가 들어 있도록 고른 것이었습니다. 실제 장애 상황에서는 정답을 모르므로, 정답을 넣고 후보를 고르는 것은 실험의 공정성을 해칩니다.

1.3 정답 없이 후보를 고르면 어떻게 되나 (TASK_069)

그래서 정답을 쓰지 않는 공개 규칙(EVT 점수: 메트릭이 얼마나 극단적으로 벗어났는지 재는 점수)으로 후보 30개를 골라 봤습니다. 결과는 다음과 같았습니다.

  • 정답 Pod의 EVT 순위: 사례별로 116위, 60위, 178위, 169위, 133/147위
  • 상위 30개 안에 정답이 든 사례: 5개 중 0개
  • EVT 점수가 대부분 0.99 이상으로 포화되어 Pod를 구별하지 못함

정답이 후보에 없으면 아무리 좋은 근거를 넣어도 정답을 맞힐 수 없습니다. 이 데이터로는 "근거를 잘 고르면 판단이 좋아지는가"를 시험할 수 없다는 결론이었습니다.

1.4 방향 전환 (2026-10-18)

여기서 연구 방향을 다시 정했습니다.

  • 기여 범주를 NLP로. 장애 분석 시스템을 만드는 것이 아니라, "LLM에게 어떤 근거를 넣어 줄 것인가"라는 근거 검색(RAG) 문제를 연구합니다. 목표 학회는 ACL, EMNLP, NAACL, EACL, COLING입니다. 장애 분석과 인과 그래프는 근거 검색이 잘 됐는지 확인하는 시험대입니다.
  • 데이터를 RCAEval로. 후보가 12개뿐이라 모든 후보에 대해 근거를 만들 수 있고, 정답이 명확한 공개 벤치마크입니다.
  • MATMCD의 위치. MATMCD의 큰 구조(데이터 → 근거 → 판단 → 제약 → 그래프)는 빌려 쓰지만, MATMCD 고유의 DA-AGENT·CC-AGENT 설계는 제안 방법에 넣지 않습니다. MATMCD는 비교용 참고값으로만 돌립니다.
  • 인과 발견 벤치마크 5종을 보조 시험대로 되살립니다. 장애 분석이 아닌 다른 분야에서도 같은 경향이 나오는지 보기 위해서입니다.

2연구 아이디어와 가설

2.1 RAG와 flat 검색

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 LLM에게 질문만 주지 않고, 관련 자료를 먼저 찾아서 함께 넣어 주는 방식입니다. LLM은 그 자료를 보고 답합니다.

자료를 찾는 가장 흔한 방법이 flat 검색입니다.

  1. 모든 자료 조각을 임베딩 모델로 숫자 벡터로 바꿔 둡니다. 임베딩 모델은 의미가 비슷한 문장일수록 비슷한 벡터를 만드는 모델이고, 이 실험에서는 BGE-M3를 씁니다.
  2. 질문 문장 하나도 벡터로 바꿉니다.
  3. 질문 벡터와 각 자료 벡터의 내적(두 벡터가 얼마나 같은 방향인지 재는 값)을 계산해, 높은 순으로 K개를 고릅니다.

2.2 flat 검색의 문제의식

인과 판단은 여러 단계의 확인이 필요한 추론입니다. "checkoutservice가 프런트엔드 지연의 원인인가"를 판단하려면

  • 두 서비스가 연결되어 있는가 (호출 관계)
  • checkoutservice에 실제로 이상이 있었는가
  • checkoutservice의 이상이 프런트엔드 지연보다 먼저 시작됐는가

를 모두 봐야 합니다. 그런데 flat 검색은 질문과 글자 그대로 비슷한 자료를 고르므로, 질문에 "frontend latency"가 들어 있으면 프런트엔드 관련 자료로 예산을 거의 다 채워 버립니다. 실제로 9장 사례에서 flat 검색이 고른 근거 24개 중 17개가 frontend 자료였습니다.

2.3 제안 아이디어: 추론 상태 기반 근거 검색

(사용자 제안 아이디어, 영문명 Reasoning-State-Aware Evidence Retrieval)

  1. 판단에 필요한 확인 단계를 추론 상태라는 종류로 미리 정해 둡니다. 예: STRUCTURE(연결 구조), CAUSE_BEHAVIOR(원인 쪽 이상), TEMPORAL_ORDER(시간 순서).
  2. 상태마다 그 상태에 맞는 자료만 남기도록 메타데이터로 거릅니다. 예: STRUCTURE 상태에서는 호출 그래프 자료만, CAUSE_BEHAVIOR에서는 원인 후보 서비스의 관측 자료만.
  3. 걸러진 자료 안에서 상태 전용 질의로 순위를 매겨 정해진 개수만 고릅니다.
  4. 어떤 상태가 필요하고 어떤 순서가 좋은지는 계획기 LLM이 사례마다 정합니다(동적 계획). 계획기에게는 정답 없이 만든 짧은 개요(어느 서비스가 언제 처음 이상해졌는지, 누가 누구를 호출하는지)를 줍니다.
  5. 어떤 상태에 맞는 자료가 하나도 없으면 대체 상태로 넘어갑니다(근거 공백 처리). 예: 직접 호출 관계가 없으면 간접 경로를 찾습니다.
  6. 근거의 총 개수는 flat과 똑같이 맞춥니다. 개수를 늘려서 이기면 의미가 없기 때문입니다.

2.4 작업 가설

공식 연구 질문(R1)은 아직 지도교수님과 확정하지 않았습니다. 실험은 다음 세 가지 작업 가설을 확인하도록 설계했습니다.

  • H1 (근거 품질). 상태 기반 검색은 flat보다 정답과 관련된 근거를 더 많이 골라 온다.
  • H2 (판단 개선). 그 결과 LLM의 최종 판단(원인 순위, 인과 그래프)이 flat보다 좋아진다.
  • H3 (동적 계획의 효과). 계획기가 사례마다 상태를 고르는 방식이, 항상 같은 상태 순서를 쓰는 방식보다 낫다.

이 셋을 분리해서 보려고 방법을 7가지 두었습니다(5장). 특히 "계획기 없이 상태를 항상 같은 순서로 쓰는 방법(state_fixed)"과 "상태 없이 자료 종류만 나눠 담는 방법(role_only)"을 넣어서, 이득이 어디서 오는지 쪼갤 수 있게 했습니다. 이런 실험을 ablation(구성 요소를 하나씩 빼 보는 실험)이라고 합니다.

그래프 계산용 노드 (출력부 A에서 사용)

PC 알고리즘은 변수당 시계열 하나가 필요합니다. 서비스마다 메트릭이 여러 개이므로 다음과 같이 하나로 합쳤습니다(결정 D-1).

  1. 서비스의 메트릭 열 중 값이 변하지 않는 열은 뺍니다.

  3. 그 z-점수들을 같은 가중치로 평균해 서비스 노드 하나로 만듭니다.
  4. KPI는 원래 값 그대로 마지막 노드로 붙입니다.

그래서 노드는 서비스 12개 + KPI 1개 = 13개입니다.

"근거 풀(corpus)"은 방법들이 근거를 골라 오는 자료 창고입니다. 모든 방법이 같은 창고에서 고르고, 고르는 방식만 다릅니다. 코드는 scripts/task070_corpus.py입니다.

4.1 카테고리 1: 사례마다 근거 단위 만들기

사례 하나의 원자료(메트릭·로그·trace)를 LLM이 읽을 수 있는 짧은 영어 문단, 즉 근거 단위로 바꿉니다. 단위에는 본문 텍스트 외에 메타데이터가 붙습니다: 역할(role: 관측 observation 또는 구조 structure), 종류(kind), 관련 서비스(services), 이상이 표시된 분(minutes). 메타데이터는 제안 방법만 걸러내기에 쓰고, flat은 텍스트만 씁니다.

① 메트릭 단위 (metric, 관측)

메트릭 열 하나당 단위 하나입니다. 분 단위 평균값을 나열하고, "사례 처음 5분"을 기준으로 크게 벗어난 분을 표시합니다.

  • 처음 5분(300초)의 평균과 표준편차를 기준선으로 삼습니다.
  • 각 시점의 z = (값 − 기준선 평균) ÷ 기준선 표준편차를 구하고, 분마다 평균합니다.
  • |z| ≥ 3인 분을 "이상 분"으로 표시합니다. 가장 크게 벗어난 시점의 z와 시각도 적습니다.

왜 처음 5분 기준인가

처음에는 사례 전체 구간의 평균을 기준으로 했는데, 장애로 값이 절반 구간 동안 올라가 있으면 전체 평균 자체가 올라가서 |z|가 1 근처로 줄어들어 이상이 가려졌습니다. 장애 주입 시각(inject_time)은 정답 정보라 쓸 수 없으므로, 정답과 무관한 고정 기준인 "처음 5분"을 썼습니다. 처음 5분에 장애가 없다는 보장은 없지만, 모든 사례·방법에 똑같이 적용되는 규칙입니다.

(실제 단위 예. 사례 ob-33f96dafc3의 u0000)

② KPI 단위 (kpi, 관측)

KPI 열에 대해 같은 방식으로 만든 단위 하나입니다. 관련 서비스는 frontend로 붙습니다.

③ 로그 템플릿 단위 (log_template, 관측)

로그 문장에는 시각, ID, 숫자 같은 바뀌는 값이 섞여 있어서 그대로는 같은 종류의 로그를 묶을 수 없습니다. 그래서 바뀌는 값을 기호로 가린 템플릿을 만들었습니다(결정 D-7).

  • 날짜·시각 → <TS>, UUID → <UUID>, 이메일 → <EMAIL>, IP → <IP>
  • 중괄호·대괄호·따옴표 안 → {<*>}, [<*>], "<*>"
  • 숫자가 섞인 8자 이상 대문자·숫자 문자열 → <ID>, 남은 숫자 → <NUM>

(서비스, 템플릿) 조합마다 단위 하나를 만들고, 총 줄 수, 로그 수준별 개수, 분당 개수, 원문 예시 하나를 적습니다. RCAEval이 제공하는 템플릿 열은 90사례 중 24사례에만 있고 평가 사례에는 하나도 없어서 쓰지 않았습니다.

5근거 고르는 방법 7가지

모든 방법은 같은 근거 풀, 같은 임베딩 모델(BGE-M3, CPU에서 FP32 정밀도, 한 번에 하나씩 계산), 같은 LLM을 씁니다. 판단 방식이 두 가지(출력부 B와 A, 6장)라서, 근거를 고르는 단위도 두 가지입니다.

  • 출력부 B: 사례 하나에 대해 근거 24개를 한 번 고릅니다.
  • 출력부 A: 변수 쌍(예: checkoutservice → KPI) 하나마다 근거 6개를 고릅니다. 사례 하나에 156쌍이므로 156번 고릅니다.

5.1 출력부 B에서의 방법 (사례당 24개)

none

근거를 넣지 않습니다. LLM이 자기 지식만으로 답합니다. "근거가 얼마나 도움이 되는가"의 기준점입니다.

flat

아래 질의 하나로 사례의 모든 단위를 점수 매겨 상위 24개를 고릅니다.

Which service caused the incident that increased frontend latency? Errors, failures, abnormal resource usage, slow or failing calls.

role_only (ablation)

상태 개념 없이 "구조 단위"와 "관측 단위"를 나눠 담기만 합니다. 구조(호출 그래프) 단위에서 flat 질의로 상위 4개, 관측 단위에서 flat 질의로 나머지 20개를 고릅니다. 사례당 구조 단위가 3개뿐이라 실제로는 3 + 21개가 됩니다.

state_fixed (ablation)

상태 4개를 항상 SYMPTOM → STRUCTURE → CANDIDATES → VERIFY 순서로 씁니다. 상태별 예산은 4, 4, 8, 8개입니다.

  • SYMPTOM (증상, 4개): frontend 관련 관측 단위 중 KPI이거나 표시된 분이 있는 것을, 질의 "frontend latency increase and failing requests"로 순위 매겨 4개.
  • STRUCTURE (구조, 4개): 호출 그래프 단위를 앞에서부터 4개(사례당 3개뿐이므로 3개 모두). 순위를 매기지 않고 풀에 들어 있는 순서대로 씁니다.
  • CANDIDATES (후보, 8개): 서비스를 "처음 이상이 표시된 분"이 빠른 순으로 정렬하고, 서비스마다 가장 일찍 이상이 시작된 메트릭 단위 1개씩, 총 8개까지.
  • VERIFY (확인, 8개): 처음 이상이 가장 빨랐던 서비스 3개를 정하고, 서비스마다 로그·trace·메트릭 관측 단위를 질의 "errors, failures or abnormal behaviour of 서비스명"으로 순위 매겨 2개씩(8÷3의 몫).
  • 중복을 빼고 24개가 안 차면 나머지를 flat 질의로 채웁니다.

state_fixed와 같은 4가지 상태를 쓰되, 계획기 LLM이 (1) VERIFY로 자세히 볼 서비스 최대 3개와 (2) 상태 순서를 정합니다. 계획기에게 주는 입력은 정답 없이 만든 개요입니다.

5.2 출력부 A에서의 방법 (쌍당 6개)

질문이 "원인 후보 A가 결과 B를 바꿀 수 있는가"라는 쌍 단위이므로, 근거도 쌍마다 고릅니다.

  • flat: 질의 "Evidence on whether A directly affects B: anomalies, errors, latency changes or call relations involving A and B."로 상위 6개.
  • role_only: A 또는 B가 관련 서비스로 붙은 단위만 남기고, 그 안에서 flat 질의로 6개.
  • state_fixed: STRUCTURE 2개 → TEMPORAL_ORDER 2개 → CAUSE_BEHAVIOR 2개(상태 판 v2 기본 순서).
  • state_dynamic: 계획기가 상태 6종 중 최대 4개를 중요한 순으로 고르고, 상태별 예산(STRUCTURE 2, TEMPORAL_ORDER 2, CAUSE_BEHAVIOR 2, EFFECT_BEHAVIOR 1, SYMPTOM 1, INDIRECT_PATH 2)을 앞에서부터 6개가 찰 때까지 배정합니다.

상태별로 근거를 고르는 풀(후보 단위 집합)은 다음과 같습니다.

상태풀고르는 방식
STRUCTUREA와 B가 둘 다 들어 있는 호출 그래프 단위상태 질의로 순위. 풀이 비면 INDIRECT_PATH로 대체
INDIRECT_PATHA 또는 B가 들어 있는 호출 그래프 단위상태 질의로 순위
CAUSE_BEHAVIORA의 관측 단위 중 표시된 분이 있는 것(없으면 A의 관측 단위 전체)상태 질의로 순위
EFFECT_BEHAVIORB에 대해 같은 규칙상태 질의로 순위
TEMPORAL_ORDERA의 메트릭 중 이상이 가장 먼저 시작된 것 1개, B의 것 1개순위 없이 그대로(시작 시각 비교용)

상태 질의는 "상태 설명: A and B" 형식입니다(예: "abnormal behaviour of the cause variable: checkoutservice and KPI_frontend_latency_p90"). 계획기에게는 A·B의 처음 이상 분과 서로 호출하는지 여부를 개요로 줍니다(9.3절에 실제 입력이 있습니다). 6개가 안 차면 flat으로 채웁니다.

5.3 카테고리 2에서의 방법 (쌍당 6개)

웹 구간에 맞춘 상태 5종을 씁니다.

상태풀
DEFINITION_CAUSE원인 변수 A가 언급된 definition 구간
DEFINITION_EFFECT결과 변수 B가 언급된 definition 구간

DIRECTIONA와 B가 모두 언급되고 "cause, lead, increase, affect, regulate..." 같은 인과 표현이 있는 relation 구간

위치 편향 줄이기

LLM은 목록 앞쪽에 나온 후보를 더 높게 매기는 경향(위치 편향)이 있습니다. 그래서 후보 순서를 3가지로 섞어 같은 질문을 세 번 합니다. 섞는 방법은 사례 ID와 반복 번호로 정한 고정 seed라서, 같은 사례에서는 모든 방법이 똑같은 세 가지 순서를 받습니다.

  3. LLM이 빠뜨린 후보는 맨 아래 자리들을 똑같이 나눠 가진 것으로 칩니다. 예: 11개를 적고 1개를 빠뜨리면 그 1개는 12위.

  1. 제약 행렬: A→B가 Yes면 "A→B 화살표는 반드시 있다(필수)", No면 "A→B 화살표는 없다(금지)"로 표시합니다. A→B와 B→A가 둘 다 Yes인 경우(양방향)도 그대로 넘깁니다(결정 D-9).
  2. PC 알고리즘(공식 코드): 13개 노드의 시계열(3.1절)과 제약을 넣어 그래프를 찾습니다. PC는 모든 노드가 연결된 상태에서 출발해, 두 노드가 다른 노드들을 고려했을 때 통계적으로 독립이면(Fisher-Z 조건부 독립 검정) 연결을 지우고, 남은 연결의 방향을 규칙으로 정합니다. 제약은 이 과정에서 배경 지식으로 반영됩니다.
  3. RWR(재시작 랜덤 워크, 공식 코드): KPI 노드에서 출발해 화살표를 거꾸로 따라 무작위로 걷다가 일정 확률로 출발점으로 돌아오기를 반복하고, 노드별 방문 횟수를 셉니다. 원인 쪽 노드일수록 많이 방문합니다. seed 0~19로 20번 돌려 각각 채점한 뒤 평균합니다(결정 D-11).

출력부 A를 보조로 내린 이유

개발 단계에서 출력부 A로 제안 방법을 시험했더니 flat보다 계속 낮았습니다(8장). 원인을 보니 상태 방법은 원인 쪽 이상 근거를 항상 넣어서 Yes가 늘었고, Yes는 "반드시 있는 화살표"가 되므로 그래프가 실제와 달라지는 정도가 커졌습니다. 근거 검색의 효과를 보려는 실험인데 그래프 단계가 결과를 크게 비트는 구조였습니다. 그래서 근거로 바로 순위를 매기는 출력부 B를 만들어 주 평가로 삼고(사용자 결정, 동결 전), 출력부 A는 보조 분석으로 남겼습니다. 카테고리 2는 그래프 자체를 평가하므로 출력부 A를 씁니다.

7.1 원인 순위 지표 (카테고리 1)

LLM이 낸 최종 순위가 아래와 같고 정답이 redis라고 합시다.

1위 cartservice   2위 frontend   3위 redis   4위 adservice   5위 ...      정답 = redis (3위)
지표뜻이 예의 값
AC@11위가 정답이면 1, 아니면 00
AC@3정답이 상위 3개 안에 있으면 11
AC@5정답이 상위 5개 안에 있으면 11
Avg@5AC@1~AC@5의 평균. RCAEval 논문의 대표 지표(0+0+1+1+1)÷5 = 0.6
RR정답 순위의 역수(Reciprocal Rank)1÷3 = 0.333

30사례의 값을 평균해 방법의 점수로 씁니다.

동점 처리

정답과 같은 점수의 후보가 여럿이면 순서를 임의로 정하지 않고, 그 동점 후보들을 무작위로 줄 세웠을 때의 기대값을 씁니다. 예를 들어 정답이 다른 후보 하나와 1~2위 동점이면 AC@1 = 0.5입니다. 이 규칙이 필요했던 이유: 출력부 A에서 그래프가 텅 비면 모든 후보가 동점인데, 공개 코드처럼 열 순서대로 줄 세우면 정답이 우연히 앞 열에 있는 사례에서 근거 없이 점수를 받는 현상이 있었습니다.

무작위 기준선

후보 12개를 완전히 무작위로 줄 세우면 AC@k의 기대값은 k÷12이고, Avg@5 = (1+2+3+4+5)÷12÷5 = 0.25, RR ≈ 0.259입니다. 실패한 실행은 이 값을 받습니다.

7.2 근거 품질 지표 (출력부 B)

"좋은 근거를 골랐는가"를 재려면 좋은 근거의 정의가 필요합니다. 사람이 판정한 근거(gold)는 없으므로 자동 규칙으로 만든 근사 정답 근거, silver 근거를 씁니다.

silver 근거의 정확한 규칙

관측 단위 중 (1) 관련 서비스에 정답 서비스가 들어 있고 (2) 표시된 분(minutes)이 비어 있지 않은 것.

여기서 주의할 점: 메트릭 단위의 "표시된 분"은 이상(|z|≥3)이 있는 분이지만, 로그·trace 단위의 "표시된 분"은 로그나 호출이 기록된 분 전체입니다. 그래서 정답 서비스의 로그·trace 단위는 거의 모두 silver이고, 메트릭 단위는 이상이 표시된 것만 silver입니다. 즉 silver는 "정답 서비스에 관한 관측 자료"에 가깝습니다. 평가에만 쓰고 방법에는 주지 않습니다.

  • 근거 정밀도: 고른 24개 중 silver의 비율. 2개면 2÷24 = 0.083.
  • 근거 재현율: 그 사례의 silver 전체 중 고른 비율.
  • 인용 정밀도: LLM이 답에서 인용한 근거(세 번의 응답 전체) 중 silver의 비율. 근거를 받은 뒤 실제로 정답 관련 근거를 짚었는지 봅니다. 인용이 하나도 없으면 계산하지 않습니다.

7.3 인과 그래프 지표 (카테고리 2)

MATMCD 공식 코드(Utils/metrics.py)를 그대로 씁니다.

  • Precision: 그린 화살표 중 정답에 있는 비율
  • F1: 정밀도와 재현율(정답 화살표 중 찾은 비율)의 조화평균. 1이 완벽, 0이 최악
  • SHD(Structural Hamming Distance): 그린 그래프를 정답 그래프로 바꾸는 데 필요한 화살표 추가·삭제·뒤집기 횟수. 0이 완벽, 낮을수록 좋음
  • FPR: 없어야 할 자리에 그린 화살표의 비율. NHD: SHD를 노드 수의 제곱으로 나눈 값

예: 정답이 A→B, B→C이고 A→B, C→B를 그렸다면 맞은 화살표 1개, 틀린 화살표 1개(방향 반대). Precision = 1/2, 재현율 = 1/2, F1 = 0.5, SHD = 1(C→B를 뒤집으면 됨).

7.4 통계: 차이가 우연인지 판단하기

30사례에서 평균이 0.848과 0.825로 다르다고 해서 한쪽이 진짜 낫다고 할 수 없습니다. 사례를 다른 30개로 뽑았다면 순서가 바뀔 수 있기 때문입니다. 그래서 두 가지 검정을 했습니다. 둘 다 같은 사례끼리 짝지어(paired) 비교합니다. 사례마다 난이도가 다르므로, 같은 사례에서 두 방법의 점수 차이를 보는 것이 더 정확합니다.

부트스트랩 95% 신뢰구간 (10,000회, seed 0)

  1. 사례마다 차이 d = (제안 방법 점수 − 상대 방법 점수)를 구합니다. 30개의 d가 생깁니다.
  2. 30개 중에서 30개를 복원 추출(뽑은 것을 다시 넣고 또 뽑기)해 평균을 냅니다.
  3. 이것을 10,000번 반복해 평균 차이의 분포를 만듭니다.
  4. 그 분포의 하위 2.5%와 상위 2.5% 지점이 95% 신뢰구간입니다.

읽는 법: 구간이 0을 포함하면 "차이가 없다"는 가능성을 배제할 수 없습니다.

부호 뒤집기 순열 검정 (100,000회, seed 0)

  1. "두 방법이 사실 같다"고 가정하면, 사례마다 d의 부호가 + 든 − 든 똑같이 그럴듯해야 합니다.
  2. 30개 d의 부호를 무작위로 뒤집어 평균을 내기를 100,000번 합니다.
  3. 그중 실제 평균 차이의 절댓값 이상으로 큰 경우의 비율이 p값입니다.

읽는 법: p < 0.05면 보통 "우연으로 보기 어렵다(유의하다)"고 말합니다.

함께 승/패/무를 적었습니다. 30사례 중 제안 방법 점수가 높은 사례, 낮은 사례, 같은 사례의 수입니다. 카테고리 2는 데이터셋이 5개뿐이라 검정하지 않았습니다.

11.1 가설별 판정

가설판정근거
H1. 상태 기반 검색은 정답 관련 근거를 더 많이 고른다부분 지지근거 정밀도·재현율은 flat의 1.5~1.7배(10.2절). 9.1절 사례처럼 flat은 질의에 끌려 증상 쪽 근거로 채워지는 경향이 있었다. 단, 인용 정밀도는 개선되지 않았다.
H2. 그 결과 최종 판단이 좋아진다지지되지 않음주 평가 차이 +0.023(p=0.76). 카테고리 2 평균 F1과 출력부 A는 flat이 앞섰다.
H3. 동적 계획이 고정 규칙보다 낫다지지되지 않음주 평가와 카테고리 2에서 state_fixed가 더 높았다. 9.2절 사례처럼 계획기가 정답 서비스를 확인 대상에서 빼는 경우가 있었다.

11.2 왜 이런 결과가 나왔을까 (원인 후보, 모두 확정 아님)

  1. 개발 사례 과적합. 상태 종류, 상태별 예산, 계획기 프롬프트를 개발 10사례만 보고 여러 번 다듬었습니다(상태 검색 v1→v2, 출력부 B v1→v3). 개발에서의 우위 +0.16(0.94−0.78)이 평가에서 +0.02로 줄어든 것은 적은 개발 사례에 맞춰진 설계가 새 사례에 일반화되지 않을 때의 전형적인 모습입니다.
  2. 표본이 작다. 30사례에서 Avg@5 차이의 신뢰구간 폭이 약 ±0.13입니다. 실제 효과가 +0.05 정도라면 이 설계로는 검출할 수 없습니다.
  3. 근거를 받는 것과 쓰는 것의 단절. 정답 관련 근거가 더 들어가도, 4B 모델이 답에서 그 근거를 짚는 비율(인용 정밀도)은 오르지 않았습니다. 병목이 검색이 아니라 판단 모델의 근거 활용 능력에 있을 수 있습니다.
  4. 계획기의 판단력. 같은 4B 모델이 계획기 역할도 합니다. 9.2절처럼 "가장 먼저 이상해진 서비스"라는 단순 규칙보다 나쁜 선택을 하는 경우가 있었습니다.
  5. 단순 구조 분리가 이득의 대부분. role_only가 주 평가 1위입니다. 호출 그래프 같은 구조 근거를 반드시 넣고 나머지를 관측 근거로 채우는 것만으로 flat보다 좋아졌고, 상태 계획이 그 위에 더하는 몫은 보이지 않았습니다.
  6. 출력부 A의 증폭 구조. 상태 방법은 Yes를 더 많이 만들고, Yes가 필수 화살표가 되면서 그래프가 실제에서 멀어집니다(9.3절 사례).
  7. 카테고리 2의 웹 근거 품질. Sachs처럼 전문 용어가 일반 웹 문서와 잘 맞지 않는 분야에서는 근거가 오히려 판단을 흐렸습니다.

11.3 MATMCD 비교에 대한 해석

MATMCD는 카테고리 1에서 PC만보다 나았지만 flat보다 낮았고, 카테고리 2의 완료된 두 데이터셋에서는 정보 없는 CC-AGENT보다 낫지 않았습니다. 이 환경(로컬 4B 모델, BGE-M3 임베딩, 공식 코드 보정 3건)에서는 논문 표 1의 MATMCD 우위를 확인하지 못했습니다. 논문은 GPT-4 계열 모델을 썼으므로 모델 차이가 큰 원인일 수 있습니다. MATMCD는 판단 경로가 우리 방법들과 달라서, 차이의 원인을 특정할 수 없는 참고값으로만 해석합니다.

12한계

  • 모델 하나. 판단과 계획 모두 로컬 Qwen3.5-4B 하나입니다. 더 큰 모델에서는 근거 품질의 이득이 판단으로 이어질 수 있지만 확인하지 않았습니다.
  • 표본과 반복. 평가 30사례, seed 하나, 한 번 실행입니다. 실행마다 결과가 얼마나 달라지는지(분산)는 재지 않았습니다.
  • silver 근거의 성격. 자동 규칙으로 만든 근사치이고, 정답 서비스의 로그·trace는 이상 여부와 관계없이 거의 모두 silver로 칩니다. 사람이 판정한 근거가 아닙니다.
  • 실패 채점. 출력부 B 7건, 출력부 A 5건(state_fixed 1, MATMCD 4)은 실제 답이 아닌 기대값입니다. 제안 방법의 실패가 3건으로 가장 많습니다.
  • KPI 선택. 프런트엔드 지연을 고정 KPI로 썼는데, 9.1절 사례처럼 KPI에 뚜렷한 이상이 없는 사례가 있습니다. 증상이 KPI에 드러나지 않는 장애에서는 질문 자체가 어려워집니다.
  • 실행 분할. 출력부 A는 세 폴더로 나눠 실행해 합쳤습니다(같은 동결 조건).
  • 원인 미확인. CUDA 오류 1건의 원인은 밝히지 못했습니다.
  • MATMCD 카테고리 2는 두 데이터셋만 완료했고, 공식 코드 보정이 필요했으며, 정답 누출 검사가 없습니다.
  • 연구 질문 미확정. 위 가설은 작업 가설이며, 공식 연구 질문은 아직 지도교수님과 합의하지 않았습니다.

1분 버전

"LLM이 인과 판단을 할 때 근거를 어떻게 골라 주느냐를 연구했습니다. 질문 하나로 비슷한 근거를 고르는 일반 RAG 대신, 판단을 구조·원인 이상·시간 순서 같은 추론 상태로 나눠 상태마다 근거를 고르는 방법을 제안했고, 마이크로서비스 장애 원인 찾기(RCAEval 30사례)와 인과 발견 벤치마크 5종으로 시험했습니다. 모든 조건을 같게 하고 방법은 결과를 보기 전에 고정했습니다. 그 결과 제안 방법은 정답 관련 근거를 1.5~1.7배 더 많이 골라 왔지만, 최종 정답률은 일반 RAG와 통계적으로 차이가 없었고(p=0.76), 계획 기능을 뺀 단순 버전이 오히려 더 좋았습니다. 4B 소형 모델이 좋은 근거를 받아도 활용하지 못하는 것이 주요 원인으로 보여, 다음 방향을 상의드리고 싶습니다."

예상 질문과 답

왜 4B 모델인가?
유료 API를 쓰지 않는 원칙으로 이 PC의 GPU에서 돌릴 수 있는 모델을 썼습니다. 더 큰 모델에서의 결과는 아직 없습니다.
30사례면 충분한가?
±0.13 정도의 신뢰구간 폭이라 작은 효과는 검출하지 못합니다. 반복 3의 30사례가 미사용으로 남아 있습니다.
정답이 새지 않았나?
사례 이름을 불투명 ID로 바꿨고, 근거 텍스트에 경로가 있으면 멈추게 했으며, 정답은 채점 단계에서만 읽습니다. 웹 근거는 정답 네트워크 페이지를 수집 전후로 차단했습니다.
결과를 보고 고친 것은 없나?
평가 전에 방법과 사례를 해시로 동결했고, 평가 결과를 본 뒤 조건을 바꾸지 않았습니다. 평가 중 문제(서버 오류, 출력 한도)는 같은 조건으로 재실행하거나 사전에 정한 실패 규칙으로 처리했습니다.
MATMCD보다는 나은가?
카테고리 1 출력부 A에서 제안 방법 0.510, MATMCD 0.407이지만 유의하지 않고(p=0.12), MATMCD는 판단 경로가 달라 직접 비교하기 어렵습니다.
