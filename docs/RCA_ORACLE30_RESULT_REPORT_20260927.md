# MATMCD 로컬 RCA 개발 실험 결과 및 논문 대비 차이 분석

작성일: 2026-09-27 · 대상: Product Review 20211203 · 실행: `20260926T143904740470Z`

## 1. 핵심 판단

이번 시험은 **로컬 PC에서 MATMCD의 RCA 처리 과정을 끝까지 실행하고, 향후 중간 로직을 교체해 비교할 기준 결과를 확보하기 위한 개발 실험**이었다. 잠정 정답 MongoDB Pod를 포함한 30개 후보에서 PC → 로그 요약/RAG → 인과관계 설명 → 제약 생성 → 그래프 재추정 → RWR 원인 순위까지 완주했다.

실행은 성공했지만, 기대했던 순위 개선은 관측되지 않았다. 잠정 정답의 **Pod 기준 순위는 PC 4위에서 MATMCD 5위로**, KPI를 포함한 공개 코드 기준 순위는 **5위에서 6위로** 내려갔다. 두 방법 모두 Pod 상위 5개에는 정답을 포함했다. 논문 표4의 PR 결과는 PC 5위 → MATMCD 2위이므로, 이번 실행의 변화 방향은 논문의 보고 방향과 다르다. [P1][E1]

다만 이번 결과는 논문과 같은 조건에서 얻은 반증이 아니다. 사례·후보 집합·전처리·LLM·임베딩·추론 설정·정답 확정 수준이 다르거나 미확인이다. 논문의 PR/CC 집계와 이번 PR 한 사례 점수를 직접 빼서 “성능이 몇 % 하락했다”고 말할 수 없다. PC의 KPI 포함 순위가 우연히 논문과 같은 5위라는 사실도 입력이나 그래프가 재현됐다는 증거는 아니다.

원인 분석에서 가장 강한 증거는 다음 세 가지다.

1. **MongoDB 장애 근거가 검색 이후 사라졌다.** 개별 로그 요약과 저장된 검색 인덱스에는 디스크 공간 부족·WiredTiger 실패가 있었지만, RAG에 실제 제공된 문맥은 다른 두 Pod의 요약이었다. 최종 노드 정보와 설명 요청 930개에는 그 구체적인 장애 표현이 전달되지 않았다.
2. **공개 코드의 그래프 설명 문제를 보존한 영향이 실제 응답에 나타났다.** 모든 설명 요청에 첫 Pod 쌍의 판정 문장이 남았고, 여러 MongoDB 관련 응답이 현재 질문과 무관한 첫 쌍을 길게 논의했다. PC 그래프의 방향을 반대로 설명하는 동작도 유지됐다.
3. **정답은 포함했지만 장애 전파 경로의 주요 Pod는 제외됐다.** 시나리오에 등장하는 ratings-v2, reviews-v1/v2/v3, productpage-v1 등이 30개 후보 밖이었다. 정답 포함은 후보 누락을 막았을 뿐, 원인 분석에 필요한 경로 보존까지 보장하지 않았다. [E2]

따라서 현재 가장 타당한 해석은 **“작은 모델 하나 때문에 실패했다”가 아니라, 불완전한 후보 그래프와 장애 근거 전달 누락, 질문/그래프 설명 불일치가 함께 존재하는 조건에서 만들어진 순위**라는 것이다. 각 요인의 순위 기여도는 대조 실험을 하지 않아 확정할 수 없다.

이 보고서는 기존 결과의 읽기·대조·결정적 계산만 수행했다. 추가 LLM 요청, 새 seed의 RWR, 전체 실험 재실행, 코드/설정 교정은 0회다. “확인 사실”, “영향을 설명하는 가설”, “추가 확인 필요”를 구분한다.

## 2. 실험 목적과 평가 대상

### 2.1 논문의 RCA 실험이 보이려던 것

논문의 §4.3은 관측 메트릭으로만 만든 PC 그래프에 로그의 의미 정보를 추가했을 때, 실제 장애 원인을 더 높은 순위로 찾을 수 있는지를 평가한다. PR·CC 데이터에는 전문가가 식별한 장애 원인은 있지만 정답 인과 그래프는 없으므로, 각 그래프에서 RWR를 수행한 원인 순위를 간접적인 품질 지표로 사용한다. 일반 인과 발견 벤치마크의 그래프 정답 비교와는 평가 대상이 다르다. [P1]

쉽게 설명하면, PC는 “어떤 Pod의 수치가 다른 Pod와 함께 움직였는가”로 연결을 추정하고, MATMCD는 “로그와 서비스 역할을 보면 그 연결이 원인 관계로 타당한가”를 검토한다. 마지막 RWR는 KPI에서 연결을 따라 이동하면서 자주 방문한 Pod를 원인 후보 상위에 둔다. 최종 정답 순위는 LLM이 직접 “정답은 MongoDB”라고 출력한 순위가 아니다.

### 2.2 이번 시험이 실제로 검증한 범위

초기 목표는 저자의 실험을 가능한 한 그대로 구성하는 것이었으나, 이후 사용자는 로컬 완주와 아이디어 비교 준비를 우선하도록 범위를 변경했다. 이번 승인 범위는 다음과 같다.

| 질문 | 이번 시험에서 답할 수 있는 범위 |
|---|---|
| 이 PC에서 전체 처리 흐름을 끝낼 수 있는가? | 승인된 30 Pod 한 사례에서 가능함을 확인 |
| 로그/RAG/설명/제약/그래프/순위가 실제로 연결됐는가? | 연결과 파일 계보를 확인. 연결됐다는 것이 정보의 의미까지 정확히 보존됐다는 뜻은 아님 |
| 이 조건에서 MATMCD가 PC보다 정답을 더 높게 찾았는가? | 이번 단일 실행에서는 그렇지 않음 |
| 원래 전체 후보에서 정답을 찾아낼 수 있는가? | 정답을 미리 후보에 넣었으므로 평가하지 못함 |
| 논문의 PR·CC 결과를 재현했는가? | 동일 사례/입력/모델 조건이 아니며 CC도 실행하지 않아 판단 불가 |
| 향후 아이디어를 비교할 기준 결과가 있는가? | 동일한 개발 조건의 기준 결과는 있음. 논문 수준 일반화에는 별도 평가 설계 필요 |

일반 인과 발견 실험, MATMCD-RE, 다른 날짜 사례, CC, API 모델 비교는 이번 실행에 포함하지 않았다. 학습이나 미세조정 실험도 아니므로 train/validation/test 분할, 학습률, epoch, optimizer는 이 실행의 설정 항목이 아니다.

### 3.2 메트릭 전처리

PR의 여섯 메트릭은 CPU 사용량, 메모리 사용량, 수신/송신 패킷률, 수신/송신 대역폭이다. 같은 KPI 키의 시각을 정확히 교집합으로 맞추고, 사용 가능한 비상수 채널에서 EVT 이상 점수를 계산했다. Pod별 여러 채널은 각 채널의 z-score를 같은 비중으로 평균해 하나의 수치 열로 만들었다.

EVT 설정은 LEMMA 참고 구현의 `d=10`, `q=0.0001`, `n_init=100`, `level=0.95`, 상·하방 탐지, `max_excess=200` 등에 근거한다. 첫100개가 정상 구간인지는 검증되지 않았다. 긴 시계열에서 한 채널이라도 양의 이상 점수가 있으면 유지하는 승인 규칙으로 218개가 모두 남았고, 이후 별도 30개 개발 후보 규칙을 적용했다.

**51,529행을 모두 썼다는 말은 이미 만들어진 임시 CSV의 모든 행을 썼다는 뜻이다.** 원배포 자료의 모든 시각을 그대로 썼다는 의미는 아니다. 앞선 교집합 정렬에서 PR 20211203은 CPU 22,982행, 메모리69행, 각 네트워크 메트릭6행이 교집합 밖으로 제외됐다. 상수 채널23개는 탐지/통합에서 제외됐다. 추가 다운샘플링, 보간, 실행을 위한 시간 구간 축소는 하지 않았다. [E4]

여러 메트릭을 한 값으로 합치는 규칙, 시간 정렬, 유지 기준은 저자의 공개 최종 CSV를 복원한 것이 아니라 승인된 로컬 가정이다. 원논문의 PR 216 Pod·길이131,329와 이번 218 Pod 준비본·51,529행은 서로 다르며, 정확히 같은 날짜/구간인지부터 미확정이므로 차이를 단순한 “논문 데이터의 일부 비율”로 해석하지 않는다.

`presence_penalty=1.5`는 실행 중 임의로 바꾼 값이 아니다. 앞선 설명41번째가 반복 출력으로8,192토큰을 소진한 뒤, 사용자 승인과 별도3건 진단을 거쳐 설명930개를 전부 새 조건으로 다시 생성했다. 기존 정상40개와 진단3개는 새 결과에 섞지 않았다. 출력 길이 감소나 정확도 향상을 보장하는 값도 아니다. [E6]

### 3.4 PC·제약·RWR·실행 환경

| 항목 | 실제 구성과 해석 |
|---|---|
| 공식 코드 | `D2I-Group/matmcd`, commit `ef2c3ecad0f5ddb9c3d20a8523c2c1043d213190` |
| 원본 유지 | 현재 RCA 공식 소스37파일 유지. 경로/로컬 모델/승인 호환 처리는 실행기에서 연결 |
| PC | causal-learn0.1.4.1, Fisher-Z, 설치 기본 alpha0.05·stable=True |
| 그래프 수정 | 생성한 제약을 BackgroundKnowledge로 전달해 같은 입력에서 PC 재실행 |
| 제약 질문 | 31×30=930개의 모든 방향쌍. A→B와 B→A는 별도 질문 |
| MATMCD 경로 | 일반 모드, RE 미사용. 최종 RWR에는 보정 그래프 사용 |
| RWR | 공개 함수, steps1000 / restart0.05 / max_self10 / 시작점Latency |
| RWR seed | 별도 seed 지정 없음. 실행 전후 NumPy RNG 상태 저장 |
| 이어받기 | MATMCD 시작 RNG는 부모 PC 종료 시 저장 상태와 동일 |
| 정렬 | 방문 횟수 내림차순, 동점은 원래 열 순서 |
| PC 사양 | RAM 약16GB, RTX2080 SUPER 8GB, Windows11/WSL2 Ubuntu |
| Python/수치 라이브러리 | Python3.11.13, NumPy2.2.6, pandas2.2.3, SciPy1.15.3 |
| 프레임워크 | PyTorch2.7.0(+cu126), LlamaIndex core0.12.37, tiktoken0.9.0 |
| GPU 런타임 | llama.cpp 전용 CUDA12.8, PyTorch CUDA12.6과 분리 |
| BGE 추가 로더 | 별도 transformers4.51.3 / safetensors0.5.3 |

seed42는 LLM 요청의 seed이며 RWR seed가 아니다. 후속 실행의 환경 snapshot은 시작/종료가 같았고 공식소스37개·설정13개·스크립트61개 해시도 일치했다. 이는 **이번 실행 도중 구성이 바뀌지 않았다는 검증**이며 저자 PC의 환경과 동일하다는 뜻은 아니다. 부모 실행의 transformers/safetensors 메타데이터 변화는 이미 설치된 승인 BGE 로더가 경로에 추가된 것으로 별도 검토했다. [E1][E7]

원본 지표 코드의 MAP@K는 표준 검색 average precision과 다른 정의다. `PRK(k)`에서 `rank < k`를 적용하고 k=1~K의 값을 평균한다. 한 사례에서는 `MAP@K=max(K-r,0)/K`가 된다. 따라서 KPI 포함5위이면 MAP@5=0, MAP@10=0.5이고, 6위이면0/0.4다. 개발용 Pod Hit@5는 `rank≤5`를 사용하므로 MATMCD가5위여서1이다. 둘의 차이는 계산 오류가 아니라 후보/KPI 포함 여부와 지표 정의의 차이다. [P2][E1]

이 단일 reciprocal rank의 상대 감소율20%를 일반적인 정확도 하락률로 해석하면 안 된다. 여러 사례 평균도 아니며 통계적 유의성을 계산하지 않았다. 정답 Pod의 방문 횟수와 같은 다른 Pod는 두 방법 모두 없으므로 정답의 순위 변화는 동점 처리만으로 생긴 차이가 아니다.

## 7. 예상과 다른 이유: 실제 증거를 따라 본 상세 분석

### 7.1 장애를 포착했지만 RAG가 다음 단계로 전달하지 못했다

**확인 사실.** 정답 Pod의 준비된 로그 프롬프트에는 `No space left on device`, `WiredTiger`, `fassert` 관련 내용이 있었다. 로컬 LLM의 개별 요약에도 디스크 공간 부족, 체크포인트 실패, 저장 엔진 panic, 프로세스 중단이 기록됐으며 상태를 심각한 실패로 설명했다. 따라서 이번 결과를 “로그가 없어서 MongoDB 장애를 전혀 볼 수 없었다”라고 설명하는 것은 틀리다. MongoDB 자체는 정확한 로그 쌍이 있는20개 중 하나다. [R1]

저장된 인덱스는31문서/31chunk였고 MongoDB 요약도 그 안에1chunk로 들어 있었다. 그 chunk에 디스크 부족 표현이 있는 것까지 확인했다. 그런데 전체 데이터셋과31개 노드를 한 번에 요약하라는 RAG 질의에 실제 제공된 문맥은 다음 두 파일뿐이었다.

- `amq-streams-cluster-operator-v1.7.3-5f6b9df578-kbgtc_summary.txt`
- `ratings-755c5794c9-m8fxz_summary.txt`

MongoDB 자체 요약은 검색 결과에 포함되지 않았다. 이는 나중에 검색을 다시 실행해서 추정한 결과가 아니라, 부모 실행의 실제 전송 요청 `call_0000021.json`에서 확인한 문맥이다. [R2]

| 전달 지점 | 디스크 부족·WiredTiger 구체 근거 |
|---|---|
| 준비된 MongoDB 로그 프롬프트 | 존재 |
| MongoDB 개별 요약 | 존재 |
| 저장된 MongoDB 검색 chunk | 존재 |
| RAG 모델에 실제 제공된 두 문맥 | 부재 |
| RAG 출력의 MongoDB 설명 | 부재 |
| 최종 node_information의 MongoDB 설명 | 부재 |
| 인과관계 설명930개 입력 | 해당 표현0/930 |
| 인과관계 설명930개 출력 | 해당 표현0/930 |

표의0/930은 대소문자를 무시한 `no space left on device`, `wiredtiger` 등 지정 문자열의 검사다. 의미가 비슷한 일반적인 “disk I/O” 언급까지 없다는 뜻은 아니다. 예를 들어480번은 일반적인 DB 병목을 이야기하지만 실제 관측된 디스크 full 사건을 인용하지 않는다.

**왜 결과에 영향을 줄 수 있는가.** “MongoDB는 데이터베이스라 성능에 영향을 줄 수 있다”와 “이 MongoDB가 현재 디스크 부족으로 쓰기 실패·중단 중이다”는 서로 다른 정보다. 후자가 사라지면 LLM은 실제 장애를 기준으로 다른 Pod와 구별하기보다 일반적인 Kubernetes/네트워크 역할로 관계를 설명하게 된다. 로그를 추가한 이점을 기대했지만, 가장 구체적인 장애 증거가 CC-agent 직전 단계에 도달하지 않은 것이다.

**책임 범위.** 이는 단순히 BGE 모델의 오류라고 확정할 수 없다. 전체 노드를 한 질의로 요청하는 설계, top-k2, 요약 문서 표현, 임베딩이 함께 작용한다. 기본k=2는 공개 호출과 설치 라이브러리의 동작을 유지한 값이지, 저자가 같은 자료에서 이 두 문서만 검색했다는 증거가 아니다. ada-002와 같은 문서로 비교하지 않았으므로 임베딩 교체가 누락을 만든 비중은 미확정이다.

또한 파서는 이 정보를 삭제하지 않았다. RAG 원문부터 이미 장애 내용이 없으며 형식 보정의 본문 보존 검사도 통과했다. 문제 위치는 **로그 확보/첫 요약 뒤, 실제 RAG 검색·합성과 노드 정보 구성 사이**로 좁혀진다.

### 7.2 확인되지 않은 관계 설명이 다음 단계에서 근거처럼 재사용됐다

**확인 사실.** 검색된 amq 요약에는 Kafka 계열 인프라가 MongoDB에 데이터를 전달할 것이라는 추정이 있었고, ratings 요약에는 PHP/PDO 연결이 정상인데도 MongoDB가 흔한 저장소이므로 관계가 있을 것이라는 설명이 있었다. 이 내용이 RAG 데이터셋 요약과 MongoDB 노드 설명에 이어졌다. 실제 최종 MongoDB 설명의 중심은 저장 역할·Kafka 파이프라인·데이터 가용성 지연이었으며, 자체 로그의 심각한 저장 장애가 아니었다. [R1][R2][R3]

논리적으로 다음 세 수준을 구분해야 한다.

1. 로그에 실제로 기록된 내용: 오류 문자열, 연결 상태, 이벤트 발생 횟수.
2. 이름/기술 스택을 보고 LLM이 붙인 해석: Kafka가 이 MongoDB에 데이터를 공급할 것이라는 구조 추정.
3. 다음 LLM이 전달받은 요약을 사실 전제로 삼아 만든 인과 설명.

2번은 서비스 manifest나 trace로 확인된 사실과 같지 않다. 그런데 공개 설명 프롬프트는 전달된 노드 정보를 “신뢰할 수 있는 출처의 정보”로 소개하므로, 추정이 반복 전달되면서 검증된 구조처럼 취급될 위험이 있다. 모든 생성 관계가 틀렸다고 단정하는 대신, **검증되지 않은 관계가 이후 판단의 전제가 됐다는 사실**을 기록한다.

구체적으로469번(MongoDB→ratings)은 PHP/PDO와 MongoDB의 구조적 불일치를 근거로 직접 인과 관계에 회의적인 설명을 만들고,1399번 제약은 `<No>`를 반환했다. 이 판단이 실제 환경에서 틀렸는지는 서비스 연결을 더 확인해야 한다. 다만 판단에 사용된 정보가 MongoDB의 실제 디스크 오류가 아니라 검색된 다른 요약의 역할 추정이었다는 점은 분명하다.

선정된 `ratings-755c5794c9-m8fxz`가 시나리오의 `ratings-v2-*`와 같은 서비스라고 이름 일부만으로 확정할 수도 없다. namespace·manifest 대응은 이 보고서에서 검증하지 않았다. “ratings”라는 부분 문자열을 근거로 두 Pod를 같은 대상으로 바꾸어 해석하지 않는다.

### 7.3 첫 번째 관계 질문이929개의 다른 질문에도 남았다

**확인 사실.** 공개 `DomainKnowledgeLLM`은 graph_prompt를 처음 한 번 만들고 재사용한다. 그 안에는 전체 그래프뿐 아니라 첫 질문의 직접 영향 판정 문장도 들어 있다. 이번 첫 쌍은 amq-streams-cluster-operator → apiserver이며, 해당 쌍에 직접 영향이 없어 보인다는 문장이 **설명 입력930개 모두**에 들어 있었다. 첫 질문을 제외한929개에서는 현재 질문과 다른 쌍의 판정이 함께 제공된 것이다. [P3][E2]

단순히 공통 배경에 첫 Pod 이름이 등장한 정도가 아니다. “위 결과에 따르면 이 두 Pod는 직접 영향을 주지 않는 것 같다”는 구체적인 판단 문장과 “이 결과가 타당한지 설명하라”는 요청이 함께 있어, 마지막에 적힌 현재 쌍과 해석 대상이 충돌한다.

| 실제 요청 | 실제 응답에서 관찰한 내용 | 이어진 제약 |
|---|---|---|
| 469: MongoDB→ratings | 현재 관계도 다루지만 첫 쌍을 먼저 판단해야 한다고 직접 언급 | 1399: No |
| 479: MongoDB→web | 주요 결론과 설명이 amq→apiserver의 직접 영향 부재에 집중 | 1409: Yes |
| 480: MongoDB→Latency | 첫 쌍의 판정을 먼저 설명한 후 DB→KPI를 일반적 병목으로 설명 | 1410: Yes |
| 916: Latency→MongoDB | 평가할 가설을 amq→apiserver로 놓고 장문의 분석 전개 | 1846: No |

이 네 건은 원문을 직접 확인한 예시다. 전체930개 중 몇 %가 의미적으로 질문을 잘못 답했는지를 전수 채점한 것은 아니다. `<Yes>/<No>` 형식이 맞았다고 해서 그 결론의 앞단 설명이 올바른 대상과 근거를 다뤘다고 볼 수 없는 이유다. [R4]

이 동작은 사용자 승인 D03 A에 따라 **알고도 공개 구현과 동일하게 유지한 항목**이다. 실행 중 새로 생긴 파일 혼합이나 실수로 옛 응답을 가져온 문제가 아니다. 저자가 표4를 얻을 때도 이 코드 경로를 그대로 썼는지는 아직 미확인이다. 코드를 고치면 새로운 비교 프로필이 되므로 이번 보고서 작성 중에는 수정하지 않았다.

### 7.4 초기 그래프를 LLM에게 설명할 때 방향이 반대로 전달됐다

PC 결과 행렬은 `A[i,j]=1`이면 **j→i**를 뜻한다. 원본 `cg2matrix`와 `matrix_to_text`도 이 규약을 따른다. 그러나 Knowledge LLM의 graph_prompt는 같은 원소를 **i가 j의 원인**이라고 설명한다. 이번 초기 PC의 확정 유향161개는 반대 방향의 문장으로 전달됐고, 무향3쌍은 양쪽 원인 문장으로 표현됐다. 총167개의 해당 문장이930개 입력 모두에 들어 있음을 확인했다. [P3][P4][E2]

실제 예를 들면 초기 `A[MongoDB,Latency]=1`은 Latency→MongoDB로 저장돼 있다. 그런데 LLM은 이를 MongoDB→Latency라는 초기 통계 결과로 읽는다.480번 응답도 모델이 제시한 방향을 MongoDB→Latency로 설명했다. 실제 PC 출력과 LLM이 이해한 PC 출력이 달라진 것이다.

이후 Yes/No 제약 행렬은 `C[원인,결과]=1` 규약을 쓰며 BackgroundKnowledge에 같은 방향으로 전달된다. **그래프 A와 제약 C는 용도가 달라 방향 규약이 다른 것이 정상**이다. 문제는 이 둘이 다르다는 사실 자체가 아니라, 그래프 A를 문장으로 옮기는 부분의 불일치다. 모든 행렬을 일괄 전치하면 해결되는 문제가 아니다.

이 동작은 통계적으로 얻은 연결을 검토한다는 MATMCD의 목적과 직접 맞닿아 있어 높은 우선순위의 검증 대상이다. 그러나 교정 후 순위가 올라갈지는 측정하지 않았다. 더 좋은 모델이 잘못된 그래프 설명을 일관되게 따를 수도 있으므로 모델 교체만으로 해결된다고 보장할 수 없다.

### 7.5 정답 포함30개가 장애 경로까지 보존한 것은 아니었다

**확인 사실.** 공식 PR 20211203 시나리오의2~4쪽은 Book-Info의 productpage/reviews/ratings/MongoDB와 외부 NFS를 설명한다. 외부 스토리지 디스크가 가득 차 MongoDB의 쓰기가 실패하고, 의존 Pod와 ratings 서비스에 문제가 전파되는 시나리오다.7쪽의 서비스 구성에는 ratings-v1/v2, reviews-v1/v2/v3 등의 대응이 나와 있다. 이는 평가용 자료로만 읽었으며 LLM에 정답 문서로 넣지 않았다. [P5]

선정 명세를 원래218개 후보와 대조하면 다음과 같다. 점수 순위는 RCA 순위가 아니라 후보를 고르는 이상 비율 순위다.

따라서 “MongoDB가 들어 있으므로 필요한 원인 정보가 충분하다”는 전제는 성립하지 않는다. 원인이 포함돼도 영향을 전달하는 서비스, 공통 원인을 구별하는 변수, KPI에 도달하는 중간 변수가 없으면 PC의 조건부 독립 검사와 RWR 경로 모두 달라진다. 정답의 로그뿐 아니라 제외된 서비스의 로그도 이번30개 RAG 문서 모음에 없었다.

이상 비율이 높은 Pod를 고르는 기준은 **장애 전파 경로를 고르는 기준과 다르다.** 장시간 높은 이상 점수가 나오는 운영/인프라 Pod가 상위에 오를 수 있고, 특정 장애 구간에서만 영향을 받는 서비스는 상대적으로 뒤로 갈 수 있다. 이번 순위 명세는 이 차이가 실제 후보 집합에 존재함을 보여 준다. 다만 점수의 높낮이가 왜 그렇게 나왔는지 채널별 전체 원인을 이 보고서에서 재추정한 것은 아니다.

정답 포함30개 방안은 계산량을 줄이고 완주를 가능하게 하는 데는 효과가 있었다. 그러나 **원래 마이크로서비스의 인과 경로를 보존하는 평가 환경으로 충분한지는 사전에 별도로 검증되지 않았다.** 이는 결과 보고에서 명시해야 할 설계 한계다. 사용자가 승인했다는 사실만으로 과학적 타당성까지 확보된 것으로 취급하지 않는다.

이 자료는 후보를 결과에 맞춰 다시 고르기 위한 근거로 쓰면 안 된다. 특히 정답 시나리오를 보고 관련 Pod만 골라 “개선된 성능”이라고 보고하면 또 다른 oracle 편향이 생긴다. 향후 후보 설계를 바꾸더라도 선정 원칙과 평가 목적을 먼저 분리하고 고정해야 한다.

### 7.6 전처리의 미확정 선택이 PC의 출발점을 바꿨을 수 있다

**확인 사실.** 최종 MATMCD용 CSV는 공개되지 않았고, 이번에는 시간 교집합·EVT 유지 기준·z-score 평균 융합을 로컬 가정으로 채택했다. 저자가 Pod별 다변량 메트릭을 어떤 방식으로 통계 그래프의 변수로 만들었는지는 확정하지 못했다.

**가능한 영향.** 한 Pod의 CPU, 메모리, 네트워크 변화를 평균하면 메트릭별 사건이 서로 희석될 수 있다. 예를 들어 표준화된 두 채널이+3과−3이면 평균은0이 된다. 이는 원리를 설명하는 가상 예시이며, 이번 MongoDB에서 실제로 그 상쇄가 일어났다고 측정한 값은 아니다. 디스크 full 장애가 PR의 CPU/메모리/네트워크6채널에 간접적으로만 나타날 수도 있으며, 어떤 메트릭이 원인 식별에 중요한지 별도 분석이 필요하다.

또한 시각 교집합과 전체 구간 융합은 비교 대상 행과 분산/상관 구조를 바꾼다. PC의 Fisher-Z는 이 수치 구조에 따라 조건부 독립을 판단하므로 프롬프트와 모델이 같아도 초기 그래프가 달라질 수 있다. 시계열의 자기상관이나 시간 지연을 이번 코드가 명시적으로 모델링하지 않는다는 점도 영향 가설이지만, 이를 이번 순위 하락의 원인으로 수치화하지 않았다.

이번 초기 PC가 정답4위라는 것은 이 출발점에서의 한 결과다. 논문과 우연히 KPI 포함5위가 같아도, 그래프 간선과 대상 변수·입력 기간이 같다는 뜻은 아니다. 저자 입력 확보 또는 별도 민감도 분석 없이는 전처리 차이의 크기와 방향을 확정할 수 없다. [E4]

### 7.7 모델·양자화·non-thinking·샘플링의 영향은 존재할 수 있지만 단독 원인으로 확정할 수 없다

GPT-4o mini에서 로컬4B Qwen Q5_K_M으로 바뀌었고, non-thinking 모드와 로컬 샘플링을 사용했다. 이는 표현 방식, 다수 노드의 관계를 구분하는 능력, 긴 문맥 속 현재 질문 유지, 불확실한 정보를 다루는 방식에 영향을 줄 수 있는 조건 차이다. 그러나 동일 입력을 두 모델에 보내 비교하지 않았으므로 “4B라서 정확도가 몇 % 낮아졌다”, “양자화 때문에5위가 됐다”는 주장은 근거가 없다.

실제 응답에서 확인한 품질 문제는 더 구체적이다.

- 469/479/916번 등의 현재 쌍과 첫 쌍 사이 혼선.
- Kafka→MongoDB 데이터 흐름 등을 검증된 구조처럼 이어서 설명하는 현상.
- 480번에서 로그 부재가 PC의 조건부 독립 검사를 직접 어렵게 한다는 취지의 설명. 이번 PC 입력은 메트릭이고 로그는 LLM 쪽으로 전달되므로 입력 역할을 혼동한 설명이다.
- 일부 응답이 관측 메트릭을 Pod의 “Latency”로 일반화한다. 실제 Pod열은 여러 메트릭의 z-score 평균이며 마지막 KPI만 Latency다.

이들은 “형식을 정상 출력했다”와 “실험 의미를 정확히 이해했다”가 다른 문제임을 보여 준다. 다만 틀린/모호한 프롬프트와 누락된 근거가 모델에 주어진 영향도 함께 있으므로 모델 능력만의 문제로 분리할 수 없다.

presence1.5는 이번930개가 출력 한도에 걸리지 않고 끝나게 했다는 실행상 근거가 있다. 이전presence0는40개 후 실패했으므로, 두 값의930개 전체 결과나 성능을 비교할 표본은 없다. “반복 억제 해결”을 “사실성 해결” 또는 “성능 개선”으로 확대하지 않는다. 출력 상한8,192를 더 올리는 것이 현재 순위 문제의 해법이라는 증거도 없다. 최대 출력은3,908로 상한 이내였다.

### 7.8 올바른 형식의 Yes/No도 서로 일관된 인과 그래프를 보장하지 않았다

모든930개 제약은 형식에 맞게 파싱됐다. 하지만 각 방향을 독립적으로 물었기 때문에 A→B와 B→A를 동시에 Yes로 정한 쌍이5개 있었다.

- MongoDB ↔ sdn-fcqbl
- packageserver ↔ Latency
- router-default ↔ sdn-xfv8t
- router-default ↔ web
- sdn-xfv8t ↔ shipping

서로 영향을 주는 현실적 피드백과 현재 정적 DAG 표현은 같은 문제가 아니다. 이처럼 두 방향을 동시에 요구한 제약은 정적 인과 그래프의 일관성 검토가 필요하다는 신호다. 다만 논문의 정답 그래프가 없으므로 어느 방향이 옳은지는 여기서 채점하지 않는다.

Yes109개 중 최종 그래프에 같은 방향으로 남은 것은69개이고40개는 남지 않았다. No 방향이 최종 간선으로 남은 경우는0이었다. 설치된 causal-learn의 skeleton 단계는 조건부 독립으로 연결을 제거하고, 배경 지식 방향화는 남아 있는 간선을 대상으로 한다. 따라서 **LLM의 Yes 행렬을 그대로 최종 인과 그래프로 복사하는 구현은 아니다.** 독립성 검정·상충 제약·방향화 과정의 결과를 함께 받는다. [P4][E2]

40개 각각이 어떤 중간 검정/충돌 때문에 빠졌는지는 중간 trace가 없어 확정하지 않는다.5개의 양방향쌍이40개 누락을 모두 설명한다고도 말할 수 없다. 이 결과는 단순히 “Yes109개면 정답 관련 간선109개가 강화됐다”라고 해석하면 안 된다는 근거다.

### 7.9 MongoDB→Latency를 찾았어도 전체 RWR 순위는 내려갈 수 있다

이번 MATMCD는 MongoDB→Latency에 Yes를 주고 최종 그래프에도 그 방향을 만들었다. 따라서 “MongoDB가 시스템 지연에 영향을 줄 수 있다는 관계를 전혀 못 찾았다”는 설명도 정확하지 않다.

RWR는 LLM의 문장이나 오류 심각도를 직접 읽지 않는다. 그래프를 입력으로 받아 경로를 따라 이동하고 방문 횟수를 센다. 따라서 하나의 중요한 간선을 찾더라도 다른 연결과 분기 수가 함께 바뀌면 전체 방문 분포는 달라진다.

**저장 그래프에서 계산한 직접적인 변화:**

| 항목 | PC | MATMCD |
|---|---|---|
| RWR가 Latency에서 한 번 이동할 수 있는 이웃 수 | 6 | 7 |
| 그중 MongoDB 포함 | 예 | 예 |
| 이동한다고 할 때 MongoDB 선택 확률 | 1/6≈16.67% | 1/7≈14.29% |
| 그 이웃의 변화 | downloads, fluentd, MongoDB, router, shipping, web | web 제외, sdn-6tgg6와 sdn-tk6x5 추가 |
| MongoDB 실제 방문 횟수 | 57 | 48 |

위 확률은 **Latency에 있고 재시작하지 않고 이동하는 경우의 한 단계 확률**이다. 전체 과정의 정답 확률이나 성능 예측값이 아니다.1000step 전체에서 각 노드를 다시 만나는 경로와 재시작·연결 부재도 함께 작용한다.

원본 RWR는 KPI와 연결된 행/열을 대칭화한다. 초기 그래프에서 Latency→MongoDB였던 연결이 최종 MongoDB→Latency로 뒤집혔어도, RWR 시작점에서는 두 경우 모두 MongoDB를 방문할 수 있다. 따라서 이 방향 수정만으로 방문 이점이 자동으로 커지지 않는다.

또한 최종 그래프에서 MongoDB의 원인으로 연결된 항목에는 ratings, 여러 SDN, shipping, migrator가 있다. RWR는 원인 방향으로 이동하므로 MongoDB에 도달한 뒤 이런 상류 후보로 계속 이동할 수 있다. 동시에 SDN 일부가 KPI의 직접 이웃으로 추가됐다. 이 구조는 SDN 방문 증가를 설명할 수 있는 실제 경로 변화다.

그러나 PC와 MATMCD의 RWR를 동일 난수 조건으로 반복 비교하지 않았다. 따라서 “첫 분기확률 감소가9회 감소를 전부 설명한다”거나 “순위 하락이 전부 그래프 때문”이라고 단정하지 않는다. 이번 보고서는 추가 난수 실험 없이 가능한 기계적 설명을 제시한 것이다.

### 7.10 단일 실행·잠정 정답·물리적 원인과 평가 노드의 차이

PC와 MATMCD 모두 한 번의 RWR 방문 횟수로 순위를 냈다.1000step은 공개 기본값이며, 여러 seed의 평균·표준편차·신뢰구간을 구하지 않았다. 한 순위 차이가 반복해서 유지되는지도 미확인이다. 저자의 MATMCD 반복 횟수와 집계 정책 역시 미공개다. 논문 부록의 best-of-10은 Efficient-CDLMs에 대한 설명이므로 MATMCD에 적용했다고 추정하지 않는다.

공식 시나리오의 물리적 장애는 **클러스터 밖 NFS 저장소의 디스크 full**이다. 이번 그래프의 평가 노드는 **MongoDB Pod**다. MongoDB는 외부 저장 장애를 직접 겪는 내부 구성요소이며 공개 보조 코드가 지정한 잠정 평가 대상이지만, “MongoDB가 최초 물리적 고장 원인”이라는 의미는 아니다.

그래프 후보에 외부 NFS가 없으므로 이 시험은 외부 원인까지 포함한 완전한 장애 설명을 점수화하지 않는다. 후보로 표현된 MongoDB를 얼마나 높게 찾았는지 측정한다. 잠정 Pod GT가 저자의 최종 표4 정답과 같은지도 추가 확인이 필요하다. 이 제약은 점수를 다른 Pod로 바꿔 높일 이유가 아니라 평가 목적을 정확히 한정할 이유다.

아래는 결과 차이를 확인하기 위한 제안이며 **이번 보고서 작성 중 적용하지 않았다.** 현재 결과를 동결하고, 사용자가 후속 방향을 정하면 필요한 변경 범위와 비용을 구체화할 수 있다.

| 검증 질문 | 가능한 분리 검증 | 해석상 주의 |
|---|---|---|
| 장애 증거 누락이 중요한가? | 전체 Pod에 동일한 규칙으로 각자 근거가 보존되는 요약/검색 방식을 별도 프로필에서 검증 | 정답 MongoDB만 선택적으로 문맥에 추가하면 정답 누출 편향 |
| 첫 쌍/그래프 방향 문제가 얼마나 영향을 주는가? | D03 교정 프로필에서 현재 쌍과 올바른 방향만 고쳐 같은 자료로 비교 | 공개 코드 보존 결과와 구분하고 두 교정을 함께/각각 한 경우를 구별 |
| 후보30개가 적합한가? | 정답을 모르는 상태에서 적용 가능한 후보/연결 보존 규칙을 먼저 설계 | 결과를 보고 후보를 다시 고르지 않음. 시나리오를 쓴 별도 oracle 진단은 성능 평가와 구분 |
| 한 순위 하락이 안정적인가? | 저장 그래프를 고정하고 사전에 정한 공통 RNG 조건/반복 수로 RWR 변동성만 비교 | 그래프 재생성과 분리. 기존 단일 결과를 새 평균으로 덮어쓰지 않음 |
| 모델 차이가 중요한가? | 동일한 질문·근거·후보의 제한된 쌍을 동일 조건으로 비교 | 현재 유료 API를 요구하는 계획으로 전환하지 않음. 모델 변경도 별도 조건 |
| 원논문과 가까운가? | 저자에게 최종 CSV/후보 목록/날짜/GT/검색/seed/실행 코드 확인 | 답변 전 추정값을 저자값으로 표시하지 않음 |

이 중 보고서가 가장 강하게 뒷받침하는 순서는 **근거 전달 확인 → 질문/방향 규약 확인 → 후보 경로의 평가 적합성 확인 → 그래프/순위의 변동성 평가 → 새 아이디어 효과 비교**다. 이는 작업을 다시 무한정 환경 설치로 돌리자는 뜻이 아니다. 이미 완료한 실행 결과를 유지하면서, 성능 비교의 의미를 훼손하는 구체적인 지점을 분리하자는 제안이다.
